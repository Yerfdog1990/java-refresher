# Iterating Over HashMaps

Source: [Iterating Over HashMaps – Baeldung](https://www.baeldung.com/members/courses/learn-java-collections/lessons/lesson-3-iterating-over-hashmaps)

## 1. Overview

Iterating over a `Map` means accessing and processing each key-value pair it stores. Unlike arrays or lists, which index data sequentially, `HashMap` stores data in no particular order — so it can't be iterated with a traditional index.

## 2. Iterating over Maps

`Map` doesn't implement `Collection` directly — a `Map` stores key-value pairs, while a `Collection` stores individual elements. Instead, `Map` provides three methods that return `Collection` views of its contents:

- `entrySet()`: a set of key-value pairs as `Map.Entry` objects
- `keySet()`: a set of the map's keys
- `values()`: a collection of the map's values

### 2.1. The entrySet() Method

Returns a `Set` view of the mappings. Each element is a `Map.Entry`, giving direct access to both key and value — usually the most efficient way to iterate when both are needed.

Example, using a `Map<String, Task>` where each Task's code is the key:

```java
@Test
void givenMapOfTasks_whenIterateEntries_thenTasksReturned() {
    for (Map.Entry<String, Task> entry: taskMap.entrySet()) {
        String key = entry.getKey();
        Task value = entry.getValue();
        System.out.println("Key: %s maps to Task: %s".formatted(key, value));
        assertEquals(key, value.getCode());
    }
}
```

`Map.Entry` provides `getKey()` and `getValue()` to access each pair directly while iterating.

### 2.2. The keySet() Method

Returns a `Set` view of the keys. More memory-efficient than `entrySet()`, so preferred when only keys are needed.

**Anti-pattern**: iterating over `keySet()` and calling `map.get(key)` repeatedly inside the loop — less efficient than `entrySet()`, since each `get()` call is a separate lookup.

```java
@Test
void givenMapOfTasks_whenIterateKeySet_thenTasksReturned() {
    for(String code: taskMap.keySet()) {
        System.out.println("Key: %s".formatted(code));
        assertTrue(code.startsWith("T"));
    }
}
```

### 2.3. The values() Method

Returns a `Collection` view of the values — not a `Set`, since a `HashMap` can map multiple keys to the same value, whereas a `Set` guarantees uniqueness. Use `values()` when only the values matter, with no concern for their keys.

```java
@Test
void givenMapOfTasks_whenIterateValuesSet_thenTaskDueDateCorrect() {
    for(Task task: taskMap.values()) {
        assertEquals(2050, task.getDueDate().getYear());
    }
}
```

## 3. Modification During Iteration

The collections returned by `entrySet()`, `keySet()`, and `values()` are live views backed by the map: changes to the map are reflected in the views, and changes to the views are reflected in the map. Not every kind of change is safe, though.

### 3.1. Setting New Values Safely

While iterating with `entrySet()`, a value can be safely redefined via `Map.Entry.setValue()`.

```java
@Test
void givenMapOfTasks_whenRedefineTaskEntry_thenValueSetSafely() {
    for (Map.Entry<String, Task> entry: taskMap.entrySet()) {
        entry.setValue(new Task(entry.getKey(), "new name", "new description", null));
    }

    Task updatedTask = taskMap.get("T001");
    assertEquals("new name", updatedTask.getName());
    assertEquals("new description", updatedTask.getDescription());
}
```

### 3.2. Mutating Values Safely

While iterating with `values()` or `entrySet()`, value objects themselves can be safely mutated (e.g., via setters).

```java
@Test
void givenMapOfTasks_whenUpdateTaskDescription_thenTaskModified() {
    String updatedDescription = "This description has been updated.";

    for (Task task: taskMap.values()) {
        task.setDescription(updatedDescription);
    }

    Task updatedTask = taskMap.get("T001");
    assertEquals(updatedDescription, updatedTask.getDescription());
}
```

Since `HashMap` uses keys (not values) for hashing and equality, mutating a value object doesn't compromise the collection's integrity.

### 3.3. Removing Entries

Calling `map.remove(key)` during iteration throws a `ConcurrentModificationException`. Safe removal requires an `Iterator` and its `remove()` method, which keeps the iteration in sync with the underlying collection.

```java
@Test
void givenMapOfTasks_whenRemoveTaskUsingIterator_thenTaskRemovedSafely() {
    Iterator<Map.Entry<String, Task>> iterator = taskMap.entrySet().iterator();
    while (iterator.hasNext()) {
        Map.Entry<String, Task> entry = iterator.next();
        if ("T001".equals(entry.getKey())) {
            iterator.remove();
        }
    }

    assertFalse(taskMap.containsKey("T001"));
    assertEquals(2, taskMap.size());
}
```

### 3.4. Unsupported Modifications

Not every structural modification is allowed during iteration:

- **Adding new entries** while iterating (via `put()`) throws a `ConcurrentModificationException`.
- **Mutating keys** is unsafe: since keys define equality and hashing, changing a key's fields while it's in the map can make the entry unreachable.

Example — adding during iteration:

```java
@Test
void givenMapOfTasks_whenPutTaskUsingIterator_thenThrowsException() {
    assertThrows(ConcurrentModificationException.class, () -> {
        Iterator<Map.Entry<String, Task>> iterator = taskMap.entrySet().iterator();
        while (iterator.hasNext()) {
            iterator.next();
            taskMap.put("T004",
              new Task("T004", "New Task", "This is a new task", LocalDate.now()));
        }
    });
}
```

This fail-fast behavior protects against unpredictable states when the map is structurally modified during iteration.

## 4. Conclusion

Because a `HashMap` stores data without guaranteed order, the only way to walk its contents is through the collection views it exposes — `entrySet()`, `keySet()`, or `values()` — each focusing on a different slice of the data.

Modifying a map during iteration follows a fail-fast contract: structural changes (additions, key-based removals) must go through the iterator itself, while in-place updates to values are always safe. Keeping that boundary in mind allows reading and writing to be combined in a single pass without breaking the map's internal consistency.
