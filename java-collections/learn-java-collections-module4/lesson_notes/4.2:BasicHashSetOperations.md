# Basic HashSet Operations

## 1. Overview

A `HashSet` provides the simplest path to enforcing uniqueness in a Java collection.

In this lesson, we'll explore each basic operation in depth and see how iteration and printing work in the absence of indexes.

## 2. Preparation

As we're about to demonstrate `HashSet`'s basic operations through unit tests, let's open the `HashSetUnitTest` class and review the initial data setup:

```java
class HashSetUnitTest {
    private final Task task01 = new Task("T01", "Another Task 01", "Another Task with code T01", null);
    // ...
    private final Task task07 = new Task("T07", "Task 07", "This is Task G", null);

    private Set<Task> tasks;

    @BeforeEach
    void resetTasks() {
        tasks = new HashSet<>(List.of(
          new Task("T01", "Task 01", "This is Task A", null),
          new Task("T02", "Task 02", "This is Task B", null),
          new Task("T03", "Task 03", "This is Task C", null),
          new Task("T04", "Task 04", "This is Task D", null)
        ));
    }
}
```

We're creating a `@BeforeEach resetTasks()` method to return a set of four prepared `Task` objects as the input for each test method. We also prepared seven `Task` objects so that test methods can reuse them for demonstrations.

Notice that `tasks` is declared as a `Set`. This highlights that the operations we'll demonstrate are common to all `Set` implementations, not just `HashSet`.

It's also important to note that while our `Task` class has four fields, its `equals()` and `hashCode()` methods only compare the `Task.code` field. This means two `Task` objects are considered equal as long as their `code` values match.

For example, `task01` is equal to the `Task` in the `tasks` set that has `code = "T01"`. As a result, our test objects `task01`–`task04` have corresponding matches in `tasks` based on their `code` values.

Next, we'll start exploring the basic operations available on sets through unit tests.

## 3. Getting the Size of a Set

We can use the standard `Collection`'s `size()` method to check how many elements a `HashSet` contains:

```java
@Test
void whenCallSizeOnTasks_thenCorrect() {
    assertEquals(4, tasks.size());
}
```

As the name implies, `size()` returns the number of elements in a `Set`.

## 4. Checking If Two HashSets Are Equal

Two `HashSet`s are considered equal if they contain the equivalent elements, regardless of order:

```java
@Test
void whenCallEqualsBetweenTwoSets_thenCorrect() {
    Set<Task> anotherSet = Set.of(task04, task01, task03, task02);
    assertTrue(anotherSet.equals(tasks));
    assertEquals(anotherSet, tasks);
}
```

As we discussed earlier, `task01`–`task04` have their corresponding matches in the `tasks` set. Therefore, `anotherSet` and `tasks` are equal. We can also verify this using JUnit's `assertEquals()` method.

## 5. Accessing Set Elements

Since `Set` doesn't support index-based element access, there's no direct way to access or point to elements within the collection selectively. Instead, we have to iterate through its elements using an enhanced for-loop or iterator.

We can also apply a more concise functional alternative, using the functional `forEach()` method to iterate over a `Set`:

```java
@Test
void whenIteratingOverTasksUsingForEach_thenCorrect() {
    tasks.forEach(task -> System.out.println(task.getName()));
}
```

In the above example, we used a [lambda](https://www.baeldung.com/java-8-lambda-expressions-tips) as the [`Consumer`](https://www.baeldung.com/java-8-functional-interfaces#Consumers) function to process each `Task` during iteration.

We simply print each `Task`'s name during iteration. Running this test produces output like:

```
Task 02
Task 01
Task 04
Task 03
```

This demonstrates that `HashSet` doesn't guarantee any specific iteration order. This is because elements are retrieved based on their hash values, not insertion sequence.

## 6. Printing the Elements in a Set

We've seen that we can print an element's information while iterating through a `Set`. Alternatively, we can directly invoke the `toString()` method on the collection itself:

```java
@Test
void whenCallPrintLnOnTasks_thenCorrect() {
    System.out.println(tasks);
}
```

`System.out.println()` implicitly calls the `Set`'s `toString()` method, producing output like:

```
[Task [code=T02, name=Task 02, description=This is Task B, dueDate=null], Task [code=T01, name=Task 01, description=This is Task A, dueDate=null], Task [code=T04, name=Task 04, description=This is Task D, dueDate=null], Task [code=T03, name=Task 03, description=This is Task C, dueDate=null]]
```

This method represents the collection by placing each element's `toString()` result between square brackets, separated by commas.

## 7. Adding Elements

A `HashSet` stores unique elements in an unordered manner. Let's explore how to add elements to a `HashSet`, including both individual and bulk operations.

### 7.1. Adding Individual Elements

Let's create a new method in the test class and add some `Task` objects to the prepared `tasks` `HashSet`:

```java
@Test
void whenAddOneTaskToTasks_thenCorrect() {
    // adding task05
    boolean addedTask05 = tasks.add(task05);
    assertTrue(addedTask05);
    assertEquals(Set.of(task01, task02, task03, task04, task05), tasks);

    // adding task01
    boolean addedTask01 = tasks.add(task01);
    assertFalse(addedTask01);
    assertEquals(Set.of(task01, task02, task03, task04, task05), tasks);
}
```

As the example shows, `add(task05)` added `task05` to `tasks` and returned `true`. Then we called `add(task01)`. `HashSet`'s uniqueness guarantee hinges on the element objects' `equals()` and `hashCode()` implementations, so `add(task01)` was rejected and returned `false`.

### 7.2. Bulk Addition

Next, let's add a second test method to demonstrate `addAll()`'s usage:

```java
@Test
void whenAddMultipleTaskToTasks_thenCorrect() {
    // adding task01, task05 and task06
    boolean addedTask010506 = tasks.addAll(List.of(task01, task05, task06));
    assertTrue(addedTask010506);
    assertEquals(Set.of(task01, task02, task03, task04, task05, task06), tasks);

    // adding Task05, task06
    boolean addedTask0506 = tasks.addAll(Set.of(task05, task06));
    assertFalse(addedTask0506);
    assertEquals(Set.of(task01, task02, task03, task04, task05, task06), tasks);
}
```

The example shows `addAll()` automatically filters duplicates when adding a collection. The `addAll()` method returns `true` if any elements were added. Otherwise, if no elements were added to the set, `addAll()` returns `false`.

## 8. Checking Membership

We often need to check whether an element exists in a `Set`. The next test shows a positive and a negative membership check using the `contains()` method:

```java
@Test
void whenCheckExistenceUsingContains_thenCorrect() {
    assertTrue(tasks.contains(task01));
    assertFalse(tasks.contains(task05));
}
```

`contains()` hashes the query element and probes its bucket directly. Since there is no scanning required, `contains()` can find the answer very fast.

Similarly, `containsAll()` allows us to check whether all elements in the given `Collection` exist in the `Set`:

```java
@Test
void whenCheckExistenceUsingContainsAll_thenCorrect() {
    assertTrue(tasks.containsAll(List.of(task01, task02)));
    assertFalse(tasks.containsAll(List.of(task01, task07)));
}
```

`containsAll()` returns `true` if the `Set` contains every element in the specified collection. If at least one element from the given collection is missing in the `Set`, `containsAll()` returns `false`.

## 9. Removing Elements

The `Set` interface provides flexible ways to remove elements, either individually or in bulk. The operations differ in their granularity and return behavior.

Next, let's explore how these operations work and understand their return values.

### 9.1. Single Removal

Let's create a new test method that removes one element and asserts that the operation succeeded and the element is gone:

```java
@Test
void whenRemoveTaskFromTasks_thenCorrect() {
    boolean removedTask01 = tasks.remove(task01);
    assertTrue(removedTask01);
    assertEquals(Set.of(task02, task03, task04), tasks);

    boolean removedTask07 = tasks.remove(task07);
    assertFalse(removedTask07);
    assertEquals(Set.of(task02, task03, task04), tasks);
}
```

As the example shows, if the element existed and was removed from the `Set`, `remove()` returns `true`. If the element wasn't found in the set, `remove()` returns `false`.

### 9.2. Bulk Removal

Let's add one more test method that bulk removes a `Collection` of `Task`s from `tasks`:

```java
@Test
void whenRemoveAllTasksFromTasks_thenCorrect() {
    // remove task01 and task05
    boolean removedTask0105 = tasks.removeAll(List.of(task01, task05));
    assertTrue(removedTask0105);
    assertEquals(Set.of(task02, task03, task04), tasks);

    // remove task01 and task07
    boolean removedTask0107 = tasks.removeAll(List.of(task01, task07));
    assertFalse(removedTask0107);
    assertEquals(Set.of(task02, task03, task04), tasks);
}
```

Similar to `addAll()`, `removeAll()` returns `true` if any elements were removed from the `Set`. Otherwise, it returns `false` if no elements were removed.

In real-world projects, we often need to remove elements that match some conditions. For that, we can't directly modify the set inside a for-each loop. Instead, we should either use an `Iterator` and its `remove()` method, or rely on the more concise `removeIf()` method (Java 8+), which applies a predicate to safely remove matching elements.

```java
@Test
void whenRemoveWithRemoveIf_thenCorrect() {
    // remove tasks by a condition
    tasks.removeIf(task -> task.getDescription().endsWith("Task A")|| task.getName().contains("03"));
    System.out.println(tasks);
}
```

Running this test produces this output:

```
[Task [code=T02, name=Task 02, description=This is Task B, dueDate=null], Task [code=T04, name=Task 04, description=This is Task D, dueDate=null]]
```

As we can see, `Task (name="Task 03")` and `Task (description="This is Task A")` have been removed from `tasks`.

### 9.3. Clearing a Set

Let's explore how to empty a `Set`:

```java
@Test
void whenClearTasks_thenCorrect() {
    tasks.clear();
    assertTrue(tasks.isEmpty());
}
```

As with any other `Collection`, `clear()` is a straightforward method that lets us remove all elements from a `Set` conveniently.

### 9.4. Replacing an Element in a Set

Unlike `List`, `Set` doesn't have a direct "replace()" operation, because sets work with unique identifiers (hash codes) rather than positional indexes. To replace an element, we simply remove the old one and then add the new one.

Next, let's explore how to replace the `Task (code="T01")`:

```java
private Task findByCode(Set<Task> set, String code) {
    for (Task t : set) {
        if (t.getCode().equals(code)) return t;
    }
    return null;
}

@Test
void whenRemoveThenAddTasks_thenTheElementGetsReplaced() {
    // can't replace directly:
    tasks.add(task01);
    assertNotSame(task01, findByCode(tasks, "T01"));

    // have to remove, then add
    tasks.removeIf(task -> task.getCode()
        .equals("T01"));
    tasks.add(task01);
    assertSame(task01, findByCode(tasks, "T01"));
}
```

## 10. Obtaining the Intersection With Another Collection

The `retainAll()` method retains only the elements in a `Set` that are also contained in a specified collection — essentially performing an intersection operation.

Next, let's create a new test method to explore `retainAll()`:

```java
@Test
void whenGetIntersectionBetweenASetAndAnotherCollection_thenCorrect() {
    List<Task> tasks010205 = List.of(task01, task02, task05);
    boolean retainAllReturn = tasks.retainAll(tasks010205);
    assertTrue(retainAllReturn);
    assertEquals(Set.of(task01, task02), tasks);
}
```

In this test, we call `retainAll()` with a list containing `task01`, `task02`, and `task05`. Since only `task01` and `task02` are present in both collections, the `tasks` set is modified to contain only these two elements, and the method returns `true` to indicate that the set was changed.

## 11. A Common Pitfall: Mutating Elements in a HashSet

When working with mutable objects in a `HashSet`, there's a subtle but critical danger that can lead to unexpected behavior and broken collections. Let's examine this pitfall through a practical example:

```java
@Test
void whenMutatingElementsInSet_thenUnexceptedResult() {
    Set<Task> myTasks = new HashSet<>();

    Task t01 = new Task("T01", "Task 01", "This is Task 01", null);
    myTasks.add(t01);
    assertTrue(myTasks.contains(t01)); // Initially present

    // modify t01.code - Dangerous!
    t01.setCode("TA");
    assertFalse(myTasks.contains(t01)); // Now missing

    // add a new taskTA to the set
    Task ta = new Task("TA", "Task TA", "This is Task TA", null);
    myTasks.add(ta);
    assertEquals(2, myTasks.size());

    System.out.println("Finally, myTasks contains:\n" + myTasks);
}
```

As we've mentioned, the `Task` class overrides `equals()` and `hashCode()` only based on its `code` field. Initially, we add `t01` to an empty `HashSet` named `myTasks`.

Then we change `t01`'s code to `"TA"`. Here is where the danger occurs. By calling `t01.setCode("TA")`, we change the object's hash code from `hash("T01")` to `hash("TA")`. However, the object remains physically stored under the original `hash("T01")` bucket, while the `HashSet` now looks for it under the new `hash("TA")`. As a result, the object gets "lost" within the `myTasks` set.

Later, we add another `Task` element `ta (code="TA")` into `myTasks`. This operation succeeds, since the set checks the bucket for `hash("TA")`, finds it empty, and accepts the new object.

Printing the elements in `myTasks` produces:

```
Finally, myTasks contains:
[Task [code=TA, name=Task 01, description=This is Task 01, dueDate=null], Task [code=TA, name=Task TA, description=This is Task TA, dueDate=null]]
```

We now have duplicate elements in a `HashSet`. This pitfall is particularly dangerous because it fails silently without exceptions, making it difficult to detect during development.

This example highlights why we should avoid mutating fields used in `equals()` or `hashCode()` while an object is stored in a `HashSet`. If we need mutable objects, we should design them so their identity is based on immutable fields, or use a different type of collection.
