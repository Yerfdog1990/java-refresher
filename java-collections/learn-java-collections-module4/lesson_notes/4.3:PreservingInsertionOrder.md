# Preserving Insertion Order (LinkedHashSet)

## 1. Overview

In Java, we often need a collection that prevents duplicate elements, just like a `HashSet`. But what if we also care about the order in which elements were inserted? This is where `LinkedHashSet` comes in.

## 2. What Is a LinkedHashSet?

First, `LinkedHashSet` is a subclass of `HashSet`. It combines the uniqueness of a `HashSet` with the predictability of order.

A `LinkedHashSet` is backed by a hash table for fast lookups and a doubly-linked list that preserves the order in which elements are inserted. This means no duplicates are allowed, and when we iterate over a `LinkedHashSet`, we see the elements in the exact order in which they were added.

Compared to `HashSet`, it uses slightly more memory but is useful whenever we need uniqueness and consistent ordering.

Next, let's take a closer look at `LinkedHashSet` through examples. We'll create tests for demos in the empty `LinkedHashSetUnitTest` class.

## 3. Constructors and Basic Usage

The `LinkedHashSet` class provides the same constructors as the `HashSet` class. That means we can create a set with default settings, or specify capacity and load factor, just like with a `HashSet`. In practice, we use them in the same way.

Let's start with the most common case: creating an empty set with the default constructor, then inserting a few `String` values and confirming that the iteration order mirrors the insertion order:

```java
@Test
void whenUsingLinkedHashSet_thenElementsPreserveInsertionOrder() {
    LinkedHashSet<String> mySet = new LinkedHashSet<>();
    mySet.add("one");
    mySet.add("two");
    mySet.add("three");
    mySet.add("four");
    assertEquals("[one, two, three, four]", mySet.toString());
}
```

As the test above shows, we inserted four `String` elements in turn into a `LinkedHashSet`, and the insertion order of the elements is preserved.

## 4. How LinkedHashSet Maintains Insertion Order

Now let's look under the hood and understand how `LinkedHashSet` maintains the insertion order.

The `LinkedHashSet` class implements the `Set` interface and the newer `SequencedSet` interface, and it directly extends `HashSet`. This means it inherits the same core API we already use with a hash-based set, while also guaranteeing that we can access elements in a well-defined sequence. What it adds is a deterministic iteration order that matches the moment each element was first seen.

Internally, the set combines two structures:

A hash table for fast lookups — each element is stored in a bucket chosen by its hash, just like in a traditional hash-based set.

A doubly linked list that threads through all elements. Every stored node carries two extra references, `prev` and `next`. The very first inserted element becomes the head, the most recent one becomes the tail, and each new element is appended at the tail. Iteration simply walks this linked list from head to tail, so we always see elements in their original insertion sequence, independent of how they are distributed across buckets.

Let's use a diagram to represent how our "one, two, three, four" example is stored in these two structures:

```
    [Hash Table (Buckets)]
    ┌─────────┐
    │ Bucket0 │ → ["two", hash=222]
    └─────────┘
    ┌─────────┐
    │ Bucket1 │ → ["one", hash=111]
    └─────────┘
    ┌─────────┐
    │ Bucket2 │ → ["four", hash=444]
    └─────────┘
    ┌─────────┐
    │ Bucket3 │ → ["three", hash=333]
    └─────────┘

   [Doubly Linked List (Insertion Order)]
     <Head>                                                            <Tail>
  ┌──────────────┐     ┌───────────────┐     ┌──────────────┐     ┌───────────────┐
  │    "one"     │     │    "two"      │     │    "three"   │     │    "four"     │
  │ prev = null  │<--->│ prev → "one"  │<--->│ prev → "two" │<--->│ prev → "three"│
  │ next → "two" │     │ next → "three"│     │ next → "four"│     │ next = null   │
  └──────────────┘     └───────────────┘     └──────────────┘     └───────────────┘
```

It's important to note that rehashing (when the table grows) doesn't affect the iteration order, since the list is separate from the bucket array.

## 5. A Practical Example of Preserving Order

The benefit of preserving insertion order becomes clear when our program's output must be predictable.

For example, let's imagine we're managing a project workflow with tasks such as coding, code review, testing, and deployment. If we use a `HashSet`, the order might change each time we run the program, leading to inconsistent task lists. With a `LinkedHashSet`, the order will always match the sequence in which the tasks were added.

Next, let's create a test to demonstrate how to maintain a project workflow using `LinkedHashSet`:

```java
@Test
void whenUsingLinkedHashSetToMaintainWorkflow_thenCorrect() {
    Task codingTask = new Task("C01", "Coding", "Implement all features of the project.", null);
    Task reviewTask = new Task("R01", "Code Review", "Review the implementation.", null);
    Task testingTask = new Task("T01", "Testing", "Test the implementation.", null);
    Task deploymentTask = new Task("D01", "Deployment", "Deploy to the production environment.", null);

    List<Task> expectedTasks = List.of(codingTask, reviewTask, testingTask, deploymentTask);

    LinkedHashSet<Task> workflow = new LinkedHashSet<>();
    workflow.add(codingTask);
    workflow.add(reviewTask);
    workflow.add(testingTask);
    workflow.add(deploymentTask);

    List<Task> tasks = new ArrayList<>(workflow);
    assertEquals(expectedTasks, tasks);
}
```

As we can see, similar to the previous "one, two, three, four" example, the `workflow` `LinkedHashSet` preserves the insertion order of the tasks.

In this test, we created the `expectedTasks` list with `Task`s in a specific sequence, then demonstrated that a `LinkedHashSet` maintains this same order when we added the four `Task`s individually and converted it back to a `List`. The assertion confirms that both lists contain identical elements in identical positions, proving order preservation.

On top of that, since `LinkedHashSet` implements the `SequencedSet` interface, it exposes methods that directly rely on ordering, such as `getFirst()` and `getLast()`.

Let's extend the test to verify these methods:

```java
assertEquals(codingTask, workflow.getFirst());
assertEquals(deploymentTask, workflow.getLast());
```

Further, when we iterate over `workflow`, we get tasks in the exact order in which they were added:

```java
Iterator<Task> iterator = workflow.iterator();
assertEquals(codingTask, iterator.next());
assertEquals(reviewTask, iterator.next());
assertEquals(testingTask, iterator.next());
assertEquals(deploymentTask, iterator.next());
```

Also, adding duplicate `Task` objects to `workflow` will be rejected, and the order of the elements is preserved:

```java
workflow.add(reviewTask);
workflow.add(testingTask);

List<Task> tasksAfterInsertDuplicate = new ArrayList<>(workflow);
assertEquals(expectedTasks, tasksAfterInsertDuplicate);
```

Finally, let's remove a task from our workflow and check if the remaining elements still preserve the insertion order. Let's say we want to skip the code review step in our workflow:

```java
workflow.remove(reviewTask);

List<Task> expectedTasksAfterRemoval = List.of(codingTask, testingTask, deploymentTask);
List<Task> tasksAfterRemoval = new ArrayList<>(workflow);
assertEquals(expectedTasksAfterRemoval, tasksAfterRemoval);
```

We can see that the insertion order is still kept after we remove elements from a `LinkedHashSet`.

These examples show why a `LinkedHashSet` is preferable whenever the output sequence matters.

## 6. Choosing Between HashSet and LinkedHashSet

`HashSet` and `LinkedHashSet` are both commonly used `Set` implementations. When deciding between them, we need to weigh memory use, performance, and whether predictable order matters:

Execution speed: both sets offer fast operations for adding, checking, and removing elements. `LinkedHashSet` introduces only a small extra cost to maintain the linked list, which is negligible in most everyday scenarios.

Memory overhead: `LinkedHashSet` requires two additional references per entry to maintain order. If we're working with millions of elements and memory is tight, this overhead might be noticeable.

Order-awareness: `HashSet` has no iteration order guarantee, while `LinkedHashSet` preserves the insertion order of elements.

Thread safety: neither implementation is thread-safe; external synchronization is needed for concurrent use.

Hash contract: mutating elements that are already stored can break the integrity of both structures, so immutability is still important.

Here's a summary to guide the choice:

| Need | Recommended Set | Notes |
|---|---|---|
| Uniqueness, order immaterial | `HashSet` | Lowest memory footprint |
| Uniqueness plus predictable iteration order | `LinkedHashSet` | Slightly higher memory, same speed, `SequencedSet` methods available |

If stable ordering is required, we should take `LinkedHashSet`; otherwise, prefer the lighter `HashSet` for pure speed.

## 7. Conclusion

In this lesson, we've explored the `LinkedHashSet` class and its distinctive characteristics. It offers the same constant-time performance as `HashSet` for basic operations, with the additional advantage of maintaining the insertion order of elements. While slightly more memory-intensive than `HashSet`, it maintains excellent efficiency for most use cases and is the ideal choice when we require both element uniqueness and predictable iteration order.

In essence, `LinkedHashSet` combines the uniqueness guarantees of a set with the iteration predictability of a list.

We've also examined its internal mechanics, learning how it maintains insertion order through a combination of hash table storage and doubly-linked list sequencing. This dual-structure approach ensures optimal performance while consistently preserving the order in which elements were added.
