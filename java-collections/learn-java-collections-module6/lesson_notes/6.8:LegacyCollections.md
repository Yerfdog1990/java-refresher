## 2. The `Vector` Class

`Vector` was Java's first resizable array implementation, introduced before `ArrayList`. `Vector` implements the `List` interface, so — like `ArrayList` — it allows duplicates and maintains insertion order.

### 2.1. Basic Operations and Synchronization

The key difference between `Vector` and `ArrayList` is that **all `Vector` methods are synchronized**, making it thread-safe.

Example — basic `Vector` usage:

```java
@Test
void whenAddingAndRetrievingWithVector_thenMaintainsOrder() {
    Vector<Task> vector = new Vector<>();
    vector.add(task01);
    vector.add(task02);
    vector.add(task03);
    vector.add(task02); // adding a duplicate

    assertEquals(4, vector.size());
    assertEquals(task01, vector.get(0));
    assertEquals(task02, vector.get(1));
    assertEquals(task03, vector.get(2));
    assertEquals(task02, vector.get(3));
}
```

`Vector` works just like an `ArrayList`, preserving insertion order and allowing duplicates. But under the hood, **every** `Vector` operation uses synchronization. Because synchronization is always applied — even when not needed — `Vector` has performance drawbacks compared to `ArrayList`.

### 2.2. `Vector` vs. `ArrayList`: A Comparison of Thread Safety

One key difference between `Vector` and `ArrayList` is thread safety. The following example creates 50 threads running in parallel, each inserting 10,000 elements into a collection.

Constants used in the test:

```java
private static final int THREADS = 50;
private static final int ELEMENTS_PER_THREAD = 10000;
```

The test uses a `CountDownLatch` to wait for every worker thread to finish before checking the final size of the collection.

**Testing with a `Vector`:**

```java
@Test
void whenUsingVector_thenItIsThreadSafe() throws InterruptedException {
    List<Integer> list = new Vector<>();
    // Note: If we use ArrayList here, it would make the test fail due to lack of synchronization
    // List<Integer> list = new ArrayList<>();

    CountDownLatch latch = new CountDownLatch(THREADS);
    for (int i = 0; i < THREADS; i++) {
        new Thread(() -> {
            for (int j = 0; j < ELEMENTS_PER_THREAD; j++) {
                list.add(j);
            }
            latch.countDown();
        }).start();
    }
    latch.await();

    assertEquals(THREADS * ELEMENTS_PER_THREAD, list.size()); // For ArrayList this would fail!
}
```

`CountDownLatch` is a concurrency utility that allows one or more threads to wait until a set of operations in other threads has completed. Here, it makes the main thread wait until all 50 worker threads finish their inserts before the assertion runs.

The test concurrently calls `vector.add()` a total of 50 × 10,000 times. The final size matches expectations exactly, because `Vector.add()` is synchronized.

**What happens with `ArrayList` instead?** After running the same test, the `ArrayList` would contain **fewer elements** than expected. This happens because `ArrayList.add()` uses an internal `size` variable to determine the index for placing new elements, and `add()` is **not** synchronized. When multiple threads call `add()` simultaneously, some writes can overwrite others, leading to lost elements and a smaller final size than expected. The higher the concurrency settings (`THREADS`, `ELEMENTS_PER_THREAD`), the higher the probability of `ArrayList` hitting thread-safety issues. **`ArrayList` is not thread-safe.**

`Vector` being thread-safe is a nice feature, but it synchronizes *everything*, incurring a performance penalty for single-threaded or predominantly read workloads.

**Recommendation:** In modern Java development, use `ArrayList` unless synchronization is specifically needed. For concurrent use cases, `CopyOnWriteArrayList` or explicit synchronization mechanisms are better options.

## 3. The `Stack` Class

`Stack` is another legacy class. It **extends `Vector`** and implements a last-in-first-out (LIFO) stack, introducing methods such as `push()`, `pop()`, and `peek()`.

Because it inherits synchronization from `Vector`, it suffers from the same performance issues.

Example — LIFO behavior:

```java
@Test
void whenPushingAndPoppingWithStack_thenFollowsLifoOrder() {
    Stack<Task> stack = new Stack<>();
    stack.push(task01);
    stack.push(task02);
    stack.push(task03);
    stack.push(task04);

    assertEquals(4, stack.size());

    assertEquals(task04, stack.pop());
    assertEquals(3, stack.size());
    assertFalse(stack.contains(task04));

    assertEquals(task03, stack.pop());
    assertEquals(2, stack.size());
    assertFalse(stack.contains(task03));

    assertEquals(task02, stack.peek());
    assertEquals(2, stack.size());
    assertTrue(stack.contains(task02));
}
```

The classic LIFO behavior is evident: the last task pushed is the first one popped. `peek()` retrieves the top element without removing it from the stack.

**Recommendation:** In modern code, use the `Deque` interface (e.g., `ArrayDeque`) for stack-like operations without the synchronization cost, and `ConcurrentLinkedDeque` in multi-threaded scenarios.

## 4. The `Hashtable` Class

`Hashtable` was the original implementation of a key-value mapping in Java. It's synchronized, making it thread-safe. Additionally, a `Hashtable` **doesn't allow `null` keys or `null` values**.

Example — `Hashtable` with `String` keys mapped to `Task` objects:

```java
@Test
void whenPuttingAndGettingWithHashTable_thenWorksButNoNullsAllowed() {
    Hashtable<String, Task> hashtable = new Hashtable<>();
    hashtable.put("the 1st task", task01);
    hashtable.put("the 2nd task", task02);
    hashtable.put("the 3rd task", task03);

    assertEquals(task01, hashtable.get("the 1st task"));
    assertEquals(task02, hashtable.get("the 2nd task"));
    assertEquals(task03, hashtable.get("the 3rd task"));

    assertThrows(NullPointerException.class, () -> hashtable.put(null, task04));
    assertThrows(NullPointerException.class, () -> hashtable.put("the 4th task", null));
}
```

`Hashtable` behaves like a `HashMap` for regular values but rejects nulls (both for keys and values), throwing `NullPointerException`.

**Locking strategy comparison — `Hashtable` vs. `ConcurrentHashMap`:**

All `Hashtable` operations are synchronized, making it less efficient than `HashMap` in single-threaded applications. In multi-threading scenarios, `ConcurrentHashMap` offers better performance than `Hashtable` because:

- `Hashtable` uses **coarse-grained locking** — the entire table is locked during operations.
- `ConcurrentHashMap` uses **fine-grained locking** — it only locks specific segments or buckets, allowing multiple threads to write to different segments simultaneously.

As a result, `ConcurrentHashMap` provides thread safety with significantly better performance than `Hashtable`.

**Recommendation:** Avoid `Hashtable` in modern code. Use `HashMap` for single-threaded scenarios and `ConcurrentHashMap` when thread safety is required.

## 5. Conclusion

The legacy collection classes `Vector`, `Stack`, and `Hashtable` remain in Java primarily for **backward compatibility** with older codebases. They still function, but are rarely used in modern applications because they rely on outdated synchronization mechanisms and lack the flexibility and performance of newer collection implementations.

For each one, the right move in new code is to reach for the modern replacement, and reserve the legacy class for situations where backward compatibility forces the issue:

| Legacy Class | Modern Replacement | Explanation |
|---|---|---|
| `Vector` | `ArrayList` / `CopyOnWriteArrayList` | `Vector` is synchronized by default, which makes it slower. `ArrayList` is preferred for most cases; `CopyOnWriteArrayList` for read-heavy concurrent cases. |
| `Stack` | `ArrayDeque` | `Stack` extends `Vector` and inherits its performance issues. `ArrayDeque` provides efficient LIFO operations without synchronization overhead. |
| `Hashtable` | `HashMap` / `ConcurrentHashMap` | `Hashtable` is synchronized and does not allow `null` keys or values. `HashMap` is faster for single-threaded use; `ConcurrentHashMap` is recommended for multithreaded contexts. |
