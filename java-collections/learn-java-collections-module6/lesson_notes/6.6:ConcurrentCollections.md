# Concurrent Collections 

## 1. Overview

In modern applications, running tasks in parallel is the norm: serving multiple users on a server, downloading files while processing data, or updating the interface while background work continues.

In a single-threaded program, collections are safe because only one piece of code can modify them at a time. With multiple threads, simultaneous updates can lead to **race conditions**, **inconsistent data**, or **runtime exceptions**.

These notes introduce synchronized wrappers first, then move on to concurrent collections designed specifically for multi-threaded use.

## 2. Synchronized Wrappers

Regular collections such as `HashMap` or `ArrayList` aren't thread-safe. If multiple threads update them at the same time, the results are unpredictable.

To handle this safely, Java provides two solutions:

- **Synchronized wrappers** — add synchronization to existing collections
- **Concurrent collections** — explicitly designed for high-concurrency use cases

Synchronized wrappers were introduced as a simple way to make existing collections thread-safe. They wrap a collection and guard every method call with a lock.

The `Collections` class provides several wrapper methods for different collection types:

- `synchronizedList`
- `synchronizedSet`
- `synchronizedSortedSet`
- `synchronizedMap`
- `synchronizedSortedMap`
- `synchronizedCollection`

The internal behavior is the same across these methods. Java provides type-specific wrappers to preserve the specialized API of each collection type, so the convenience of the original API isn't lost.

### 2.1. Example With Synchronized Wrappers

An example of a regular collection wrapped for safe use in a multithreaded application:

```java
@Test
void givenSynchronizedTaskList_whenMultipleThreadsAdd_thenAllTasksRecordedButSlower()
  throws InterruptedException {
    List<String> list = Collections.synchronizedList(new ArrayList<>());

    Runnable writer = () -> {
        for (int i = 0; i < 100; i++) {
            list.add("Task-" + i);
        }
    };

    Thread t1 = new Thread(writer);
    Thread t2 = new Thread(writer);

    t1.start();
    t2.start();
    t1.join();
    t2.join();

    assertEquals(200, list.size());
}
```

Both threads add elements safely because wrapping the `ArrayList` with `Collections.synchronizedList()` ensures every operation is protected by the same lock. The trade-off: every method call is serialized, introducing contention that can slow things down as more threads are involved.

**What happens with a plain `ArrayList` instead?** The code would still compile, but behavior becomes unpredictable once multiple threads start writing to it. Two threads could interfere with each other while updating the internal array, and if another thread were iterating at the same time, a `ConcurrentModificationException` could occur.

### 2.2. Limitations of Synchronized Wrappers

While synchronized wrappers make collections safe for multi-threaded use, they have real drawbacks:

- **Coarse-grained synchronization** — the entire collection is locked for each operation, which can reduce performance when many threads are accessing it.
- **Potential contention** — multiple threads must wait for access, potentially slowing down concurrent applications.
- **Iteration isn't automatically safe** — even though individual methods like `add` or `get` are synchronized by the wrapper, iteration involves multiple calls (creating the iterator, moving to the next element, reading values). The wrapper cannot guarantee thread-safety across that whole sequence on its own. To avoid race conditions or `ConcurrentModificationException`, iteration typically needs to be placed manually inside a `synchronized` block.

Synchronized wrappers are useful for simple scenarios or legacy code, but for high-concurrency applications, concurrent collections are generally preferred — they let multiple threads work with the same collection with better concurrency and efficiency than synchronized wrappers offer.

## 3. The `java.util.concurrent` Package

The `java.util.concurrent` package was introduced to simplify and strengthen support for multithreaded programming. Without it, low-level constructs like `Thread`, `synchronized`, and `wait`/`notify` would have to be handled manually — often error-prone and difficult to manage in larger applications.

This package provides high-level utilities that make writing safe, scalable, and efficient multi-threaded code much easier. Main categories include:

- **Executor Framework** — run tasks in a pool of threads instead of managing threads manually (e.g., `Executor`, `ExecutorService`)
- **Concurrent Collections** — thread-safe versions of common data structures. Besides the collections covered in this lesson (`ConcurrentHashMap`, `CopyOnWriteArrayList`), the package also provides:
    - `ConcurrentSkipListMap` and `ConcurrentSkipListSet` — sorted, thread-safe alternatives to `TreeMap` and `TreeSet`
    - `ConcurrentLinkedQueue` and `ConcurrentLinkedDeque` — efficient non-blocking queues and deques
    - **Blocking Queues** such as `ArrayBlockingQueue`, `LinkedBlockingQueue`, or `PriorityBlockingQueue` — useful for producer–consumer patterns
- **Synchronizers** — tools to coordinate threads, such as making them wait for each other (e.g., `CountDownLatch`, `CyclicBarrier`, `Semaphore`, `Exchanger`)
- **Locks** — flexible alternatives to the `synchronized` keyword (e.g., `ReentrantLock`, `ReadWriteLock`)
- **Atomic Variables** — classes for safely updating numbers or references without using locks (e.g., `AtomicInteger`, `AtomicLong`, `AtomicReference`)

The rest of these notes focus on concurrent collections, which overcome the limitations of synchronized wrappers and are optimized for multi-threaded access patterns.

## 4. `ConcurrentHashMap`

`ConcurrentHashMap` is a thread-safe alternative to `HashMap`. It implements `ConcurrentMap` and extends `AbstractMap`.

Unlike `HashMap`, it:

- Allows concurrent read and write operations **without manual synchronization**
- Does **not** allow `null` keys or `null` values

This makes it especially useful in multi-threaded environments where multiple threads frequently access and modify shared data.

### Example: caching tasks by ID

A realistic scenario — caching tasks by ID where multiple threads may try to fetch or insert tasks at the same time (using a `Task` model with fields `code`, `name`, `description`, and `dueDate`):

```java
@Test
void givenConcurrentTaskCache_whenMultipleThreadsInitialize_thenTaskCreatedOnce() throws InterruptedException {

    ConcurrentHashMap<String, Task> taskCache = new ConcurrentHashMap<>();
    Runnable worker = () -> taskCache.computeIfAbsent("001", id -> new Task(id, "Generated Task", "Created once", null));

    Thread t1 = new Thread(worker);
    Thread t2 = new Thread(worker);

    t1.start();
    t2.start();
    t1.join();
    t2.join();

    assertEquals(1, taskCache.size());
    assertEquals("Generated Task", taskCache.get("001").getName());
}
```

Two threads both attempt to insert a task with the same ID. `computeIfAbsent()` checks whether the key is already present, and if not, uses the provided function to create a new value — and this **check-and-insert happens atomically**, so only one thread actually creates the new task. The other thread reuses the task that was already made.

This is different from a synchronized wrapper, which only locks individual method calls. There, `get()` and `put()` could still interleave across threads, leading to duplicate entries.

> **Note:** The variable is declared as `ConcurrentHashMap` (not just `Map`) to make the intent clear — this specific implementation is chosen deliberately for thread-safety.

### `ConcurrentHashMap` vs. `Collections.synchronizedMap()`

Both provide thread safety, but in very different ways:

| | `Collections.synchronizedMap()` | `ConcurrentHashMap` |
|---|---|---|
| Mechanism | Wraps a regular `Map` (e.g., `HashMap`); every method call synchronizes on a **single lock** | Fine-grained locking (and lock-free techniques for some operations) across different buckets |
| Individual ops (`get`, `put`) | Safe on their own | Safe on their own |
| Compound ops (`computeIfAbsent`, `putIfAbsent`, `replace`, `remove(key, value)`) | **Not atomic** — e.g., default `computeIfAbsent` is just a `get()` followed by a `put()`; two interleaving threads can both insert the same key, causing duplicate work or inconsistent results | **Atomic** — correctness under concurrency without extra synchronization from the developer |
| Concurrent reads | Blocked by the single lock | Generally **non-blocking** |
| Concurrent writes | Serialized across the whole map | Threads can update concurrently as long as they touch different buckets |
| Scalability | Poor under contention | Scales well, especially for **read-heavy** workloads |

## 5. `CopyOnWriteArrayList`

`CopyOnWriteArrayList` is a thread-safe variant of `ArrayList` found in `java.util.concurrent`. As the name suggests, it creates a **new copy of the underlying array every time a modification occurs** (such as `add`, `set`, or `remove`).

This design ensures iteration can proceed safely without explicit synchronization, since iterators operate on a **snapshot** of the list taken at the time of their creation.

This type of list is beneficial when reads are frequent and writes are rare, since modifications incur extra cost from copying.

### Example: registered observers

Maintaining a list of registered observers that can be read safely while others register at the same time:

```java
@Test
void givenObserverList_whenIteratingAndAdding_thenIterationUsesSnapshot() throws InterruptedException {
    CopyOnWriteArrayList<String> observers = new CopyOnWriteArrayList<>();
    observers.add("Observer A");
    observers.add("Observer B");

    List<String> seenDuringIteration = new ArrayList<>();
    Thread reader = new Thread(() -> {
        for (String obs : observers) {
            seenDuringIteration.add(obs);
            try {
                Thread.sleep(50); // simulate slow iteration
            } catch (InterruptedException ignored) {}
        }
    });

    Thread writer = new Thread(() -> {
        observers.add("New Observer A");
        observers.add("New Observer B");
    });

    reader.start();
    writer.start();
    reader.join();
    writer.join();

    // The iterator only saw the original snapshot even if we add new items to the list
    assertEquals(List.of("Observer A", "Observer B"), seenDuringIteration);

    // The new observers were added, but only visible after iteration
    assertTrue(observers.contains("New Observer A"));
    assertTrue(observers.contains("New Observer B"));
}
```

When the loop starts, the iterator takes a snapshot of the list containing `"Observer A"` and `"Observer B"`. Even though new elements are added during the loop, the iterator doesn't see them — they only appear in the list after the iteration finishes.

This snapshot behavior is what makes `CopyOnWriteArrayList` safe for concurrent iteration and modification: readers never see a moving target, so they always work with a consistent view of the data.

### Trade-offs

- **Writes are costly** — each change makes a new copy of the array.
- **Iterators don't reflect concurrent writes** — readers can see outdated (stale) data.
- **Memory overhead** — multiple copies of the array may exist during modification.

Overall, `CopyOnWriteArrayList` is best suited for **read-heavy scenarios**.

---

## 6. Conclusion

The `java.util.concurrent` package takes away much of the low-level complexity of thread management, making multithreaded programming simpler and more reliable.

The key takeaway: **thread-safety isn't a single recipe** — picking the right tool depends on the access pattern.

- **Map-style caches and registries** that take heavy concurrent writes benefit from atomic compound operations and fine-grained locking → `ConcurrentHashMap`
- **List-style data accessed mostly by readers** benefits from snapshot semantics → `CopyOnWriteArrayList`

Choosing the implementation that fits the workload — rather than reaching for a one-size-fits-all wrapper — lets development focus on solving real problems instead of working around concurrency pitfalls.

### Quick reference

| Implementation | Thread-Safety Strategy | Nulls Allowed? | Best For |
|---|---|---|---|
| `Collections.synchronizedX()` | Single lock wraps every method call | Depends on wrapped collection | Simple scenarios, legacy code |
| `ConcurrentHashMap` | Fine-grained locking / lock-free; atomic compound operations | No (neither keys nor values) | High-concurrency map access, especially read-heavy |
| `CopyOnWriteArrayList` | Copies the array on every write; iterators use a snapshot | Depends on usage | Read-heavy, write-rare lists (e.g., observer/listener lists) |
