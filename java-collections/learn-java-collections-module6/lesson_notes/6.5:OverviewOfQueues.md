# Overview of Queues 

## 1. Overview

Queues are part of the Java Collections Framework, and they hold elements that wait to be processed in a specific order.

These notes cover the contract of a queue, the core behaviors it exposes, and the most commonly used implementations the JDK ships.

## 2. The Importance of Queues

Queues are one of the most fundamental data structures in computer science. Their defining feature is **FIFO (first in, first out)** ordering: the first element added is the first one removed — just like people lining up at a supermarket checkout, where whoever arrives first gets served first.

A queue has two primary operations:

- **enqueue** — inserts an element at the back
- **dequeue** — removes an element from the front

### Internal implementations

A queue can be implemented internally in several ways, though these details are usually hidden by standard library implementations:

- **Linked list** — each element points to the next.
- **Circular buffer** — a fixed-size array that wraps around, avoiding element shifting and staying memory-efficient.

### Real-world examples

Queues show up constantly in everyday systems, always processed in arrival order:

- People lining up at a checkout
- Tasks waiting in a printer queue
- Customer requests handled by a web server
- Packets buffered in a network router
- Background jobs scheduled by an operating system

## 3. The `Queue` Interface

The `Queue` interface (`java.util`) defines three basic categories of operations: adding elements, checking the head element, and removing elements.

Each category has **two variants**:
- One that **throws an exception** if the operation fails
- One that **returns a special value** (`null` or `false`)

This design lets the caller choose how to handle empty or full queues.

| Operation | Throws Exception | Returns Special Value |
|---|---|---|
| Insert | `add(e)` | `offer(e)` |
| Examine head | `element()` | `peek()` |
| Remove head | `remove()` | `poll()` |

### 3.1. `add()` vs `offer()`

Both insert an element. The difference is how they handle **capacity-restricted** queues:

- `add()` throws an exception (`IllegalStateException`) if the element cannot be added due to capacity limits.
- `offer()` simply returns `false` in the same case.

**Unbounded queue example** — with an unbounded queue (`LinkedList`), there's no practical difference, which is the most common case in practice:

```java
@Test
void givenQueueMethods_whenComparingAddAndOffer_thenBothAddElements() {
    Queue<Task> taskQueue = new LinkedList<>();

    taskQueue.add(new Task("001", "Task added with add()", "Using add method", null));
    taskQueue.offer(new Task("002", "Task added with offer()", "Using offer method", null));

    assertEquals(2, taskQueue.size());
}
```

**Bounded queue example** — bounded queues are sometimes used in multithreaded environments. Since `ArrayDeque` itself is unbounded (its integer constructor argument is only an *initial-capacity hint*), a bounded queue can be simulated with manual size guards:

```java
@Test
void givenBoundedArrayDeque_whenComparingAddAndOffer_thenOfferReturnsFalseAddThrows() {
    int capacity = 2;
    ArrayDeque<Task> boundedQueue = new ArrayDeque<>(capacity);

    boundedQueue.offer(new Task("001", "First Task", "First task", null));
    boundedQueue.offer(new Task("002", "Second Task", "Second task", null));

    boolean offerResult = (boundedQueue.size() < capacity) &&
      boundedQueue.offer(new Task("003", "Task added with offer()", "Using offer method", null));
    assertFalse(offerResult);

    assertThrows(IllegalStateException.class, () -> {
        if (boundedQueue.size() >= capacity) {
            throw new IllegalStateException("Queue full");
        }
        boundedQueue.add(new Task("003", "Task added with add()", "Using add method", null));
    });

    assertEquals(2, boundedQueue.size());
}
```

The first attempt via `offer()` returns `false`; the attempt via `add()` throws `IllegalStateException`. The queue stays at 2 elements throughout.

### 3.2. `element()` vs `peek()`

Both check the head element **without removing it**.

**Non-empty queue** — both return the head, and the element stays in the queue:

```java
@Test
void givenNonEmptyQueue_whenComparingElementAndPeek_thenBothReturnHead() {
    Queue<Task> taskQueue = new LinkedList<>();
    Task testTask = new Task("001", "Test Task", "Test description", null);
    taskQueue.offer(testTask);

    Task peekedTask = taskQueue.peek();
    assertEquals("Test Task", peekedTask.getName());

    Task elementTask = taskQueue.element();
    assertEquals("Test Task", elementTask.getName());
    assertEquals(1, taskQueue.size());
}
```

**Empty queue** — behavior diverges:

```java
@Test
void givenEmptyQueue_whenComparingElementAndPeek_thenDifferentBehavior() {
    Queue<Task> emptyQueue = new LinkedList<>();
    Task peekedTask = emptyQueue.peek();
    assertNull(peekedTask);

    assertThrows(NoSuchElementException.class, () -> {
        emptyQueue.element();
    });
}
```

- `peek()` returns `null`
- `element()` throws `NoSuchElementException`

### 3.3. `poll()` vs `remove()`

Behavior mirrors `element()`/`peek()`, except these methods **also remove** the head element.

**Non-empty queue** — both behave the same, removing elements in FIFO order:

```java
@Test
void givenNonEmptyQueue_whenComparingRemoveAndPoll_thenBothRemoveHead() {
    Queue<Task> taskQueue = new LinkedList<>();
    taskQueue.offer(new Task("001", "First Task", "First", null));
    taskQueue.offer(new Task("002", "Second Task", "Second", null));

    Task polledTask = taskQueue.poll();
    assertEquals("First Task", polledTask.getName());

    Task removedTask = taskQueue.remove();
    assertEquals("Second Task", removedTask.getName());

    assertTrue(taskQueue.isEmpty());
}
```

**Empty queue** — behavior diverges:

```java
@Test
void givenEmptyQueue_whenComparingRemoveAndPoll_thenDifferentBehavior() {
    Queue<Task> emptyQueue = new LinkedList<>();

    Task polledTask = emptyQueue.poll();
    assertNull(polledTask);
    assertThrows(NoSuchElementException.class, () -> {
        emptyQueue.remove();
    });
}
```

- `poll()` returns `null`
- `remove()` throws `NoSuchElementException`

## 4. Types of Queues

The JDK provides two groups of `Queue` implementations:

1. **General-purpose implementations** — follow plain FIFO order.
2. **Ordered queues** — decide the head based on element ordering rather than insertion order.

### 4.1. General-Purpose Implementations

The two most commonly used classes implementing `Queue`:

- **`LinkedList`** — essentially a chain of connected nodes, which fits naturally with the queue concept.
- **`ArrayDeque`** — uses a circular buffer internally. It uses `null` values internally as a divider, so **`ArrayDeque` cannot store `null` elements**.

(Examples for both were shown in Section 3 above.)

### 4.2. Ordered Queues

Sometimes elements should come out in **priority order** rather than insertion order. Common use cases:

- Processing the most urgent task first
- Picking the next item in graph algorithms (e.g., shortest-path search)
- Always returning the smallest-cost candidate from a worklist

An ordered queue determines its head based on element ordering. Ordering can be defined in two ways:

- **Natural order** — elements implement [`Comparable`](https://www.baeldung.com/java-comparator-comparable#comparable)
- **Custom order** — supplied via a [`Comparator`](https://www.baeldung.com/java-comparator-comparable#comparator)

#### Natural ordering with `Comparable`

First, the `Task` class implements `Comparable<Task>`:

```java
public class Task implements Comparable<Task> {
    // ...

    @Override
    public int compareTo(Task other) {
        if (this.dueDate == null && other.dueDate == null) {
            return this.code.compareTo(other.code);
        }
        if (this.dueDate == null) {
            return 1;
        }
        if (other.dueDate == null) {
            return -1;
        }
        int dateComparison = this.dueDate.compareTo(other.dueDate);
        if (dateComparison != 0) {
            return dateComparison;
        }
        return this.code.compareTo(other.code);
    }
}
```

This compares tasks by due date first, falling back to `code` as a tiebreaker when due dates are equal or both `null`.

With natural order defined, `PriorityQueue` can be used directly:

```java
@Test
void givenPriorityQueue_whenUsingNaturalOrdering_thenTasksOrderedByDueDate() {
    PriorityQueue<Task> naturalOrder = new PriorityQueue<>();

    naturalOrder.offer(new Task("003", "Write report", "Write quarterly report", LocalDate.of(2025, 10, 25)));
    naturalOrder.offer(new Task("001", "Deploy application", "Deploy to production", LocalDate.of(2025, 10, 15)));
    naturalOrder.offer(new Task("002", "Schedule meeting", "Schedule team meeting", LocalDate.of(2025, 10, 20)));

    Task firstTask = naturalOrder.poll();
    assertEquals("001", firstTask.getCode());

    Task secondTask = naturalOrder.poll();
    assertEquals("002", secondTask.getCode());

    Task thirdTask = naturalOrder.poll();
    assertEquals("003", thirdTask.getCode());
}
```

Elements are polled out in order of due date, regardless of insertion order.

#### Custom ordering with `Comparator`

For a different processing rule — e.g., ordering by task name length — pass a `Comparator` to the `PriorityQueue` constructor:

```java
@Test
void givenPriorityQueue_whenUsingCustomOrdering_thenTasksOrderedByNameLength() {
    PriorityQueue<Task> byLength = new PriorityQueue<>(Comparator.comparingInt(task -> task.getName().length()));

    byLength.offer(new Task("001", "Write documentation", "Write user documentation", null));
    byLength.offer(new Task("002", "Review code", "Review pull request", null));
    byLength.offer(new Task("003", "Test", "Run unit tests", null));

    Task firstTask = byLength.poll();
    assertEquals("Test", firstTask.getName());

    Task secondTask = byLength.poll();
    assertEquals("Review code", secondTask.getName());

    Task thirdTask = byLength.poll();
    assertEquals("Write documentation", thirdTask.getName());
}
```

This approach is useful when prioritization needs to follow specific conditions — tackling the simplest tasks first, focusing on the most critical meetings, or implementing algorithms like Dijkstra's shortest path.

---

## 5. Conclusion

A queue is a small contract built around a single idea: **hand back elements in a predictable order**. The chosen implementation decides what "predictable" means in practice:

- **FIFO insertion order** for general-purpose implementations (`LinkedList`, `ArrayDeque`)
- **Element-driven priority order** when the most important item needs to be processed next (`PriorityQueue`)

### Decision axes

When choosing an implementation, two questions point straight to the right choice:

1. Should **arrival order** or **element ordering** decide the head?
2. Does the queue need to be **bounded** or **null-friendly**?

### Quick reference

| Implementation | Order | Nulls Allowed? | Notes |
|---|---|---|---|
| `LinkedList` | FIFO (insertion) | Yes | Unbounded; node-chain based |
| `ArrayDeque` | FIFO (insertion) | No | Unbounded; circular buffer; `null` used internally as divider |
| `PriorityQueue` | Natural (`Comparable`) or custom (`Comparator`) | No | Head is always the "smallest" per ordering, not oldest |
