## 2. Selection Process for a Top-Level Type

The Java Collections Framework defines four principal interfaces: **`List`**, **`Set`**, **`Map`**, and **`Queue`** — each representing a specific type of data collection.

### Decision tree: which top-level type?

The tree starts with the general question *"Which Collection type to use?"* and branches out based on three refining questions:

```
Which Collection type to use?
│
├─ 1. Store key-value pairs?
│     ├─ Yes ────────────────────────────► Map
│     └─ No, continue to question 2
│
├─ 2. Require unique elements?
│     ├─ Yes ────────────────────────────► Set
│     └─ No, continue to question 3
│
└─ 3. Use a processing order?
      ├─ Yes ────────────────────────────► Queue
      └─ No ─────────────────────────────► List
```

**1. Store key-value pairs?** This question separates the `Map` interface from all other `Collection` interfaces.
- **Yes** → choose a `Map`.
- **No** → move to the next question.

**2. Require unique elements?** This determines whether duplicates are allowed in the group of elements.
- **Yes** → choose a `Set`.
- **No** → move to the next question.

**3. Use a processing order?** This asks whether elements need to be accessed or removed in a specific, predefined order.
- **Yes** → choose a `Queue`. Although some other collection types provide a form of ordering, `Queue`'s primary purpose is to model a collection for holding elements before processing.
- **No** → use a `List`.

**General rule of thumb:** `List` is the default best choice for general-purpose use, since it combines ordered elements with indexed access.

## 3. Choosing an Implementation Type

Once the top-level type (`List`, `Map`, `Set`, or `Queue`) is decided, the next step is selecting a specific implementation class.

### 3.1. Choosing a `List`

```
Need frequent random access by index?
├─ Yes ─────────────────────────────► ArrayList
└─ No, continue

Frequent insert/remove using an iterator?
├─ Yes ─────────────────────────────► LinkedList
└─ No ──────────────────────────────► ArrayList (fallback)
```

1. **Need frequent random access by index?**
    - **Yes** → `ArrayList` is the best option.
    - **No** → move to the next question.
2. **Frequent insert/remove using an iterator?**
    - **Yes** → `LinkedList` is the best option.
    - **No** → the recommended choice falls back to `ArrayList`.

### 3.2. Choosing a `Set`

```
Preserve insertion order?
├─ Yes ─────────────────────────────► LinkedHashSet
└─ No, continue

Sorted elements storage?
├─ Yes ─────────────────────────────► TreeSet
└─ No ──────────────────────────────► HashSet (default)
```

1. **Preserve insertion order?**
    - **Yes** → `LinkedHashSet` is the best option.
    - **No** → move to the next question.
2. **Sorted elements storage?** This asks whether elements must be stored and iterated over based on their natural ordering or a custom comparator.
    - **Yes** → `TreeSet`, to keep elements in sorted order.
    - **No** → `HashSet` — the most common default implementation, since neither insertion order nor sorted order is required.

### 3.3. Choosing a `Map`

The choice of a `Map` implementation follows similar logic to `Set`, but the decision is based on the ordering of the **keys**:

```
Preserve insertion order of keys?
├─ Yes ─────────────────────────────► LinkedHashMap
└─ No, continue

Sorted keys storage?
├─ Yes ─────────────────────────────► TreeMap
└─ No ──────────────────────────────► HashMap (default)
```

1. **Preserve insertion order of keys?**
    - **Yes** → `LinkedHashMap` is the best option.
    - **No** → move to the next question.
2. **Sorted keys storage?**
    - **Yes** → `TreeMap`, to keep keys in sorted order.
    - **No** → default to `HashMap`.

### 3.4. Choosing a `Queue`

When the top-level type is a `Queue`, a different set of refining questions applies:

```
Ordered by natural or custom ordering?
├─ Yes ─────────────────────────────► PriorityQueue
└─ No, continue

Need List API or allow null elements?
├─ Yes ─────────────────────────────► LinkedList
└─ No ──────────────────────────────► ArrayDeque
```

1. **Ordered by natural or custom ordering?**
    - **Yes** → `PriorityQueue`.
    - **No** → move to the next question.
2. **Need `List` API or allow `null` elements?**
    - **Yes** → `LinkedList`, if the queue also needs to function as a `List`, or if `null` elements must be allowed.
    - **No** → `ArrayDeque`, if only queue/stack functionality (FIFO/LIFO) is needed, with a faster implementation, and `null` elements aren't required.

## 4. Key Factors

The choice of Java Collection relies on four main factors: **ordering**, **uniqueness**, **access patterns (performance)**, and **thread-safety**. Together, these are the building blocks behind the decision trees above, and understanding them helps reason about cases the trees don't cover directly.

### 4.1. Ordering

Collections are grouped by how they manage the sequence of their elements:

- **Insertion Order** — `List` types and their ordered counterparts maintain the exact sequence in which elements were added. Lists also offer positional (index-based) access.
- **End-point Order** — `Queue` types strictly manage element removal from the head, essential for FIFO/LIFO processing flow. They generally don't support efficient random access to the middle.
- **Sorted Order** — `TreeSet` and `TreeMap` automatically arrange elements or keys according to their natural sorting order (or a custom `Comparator`).
- **No Specific Order** — `HashSet` and `HashMap` offer the fastest performance by organizing elements based on their hash code, with no guarantee of iteration order.

### 4.2. Uniqueness

This factor determines whether a collection allows or enforces the exclusion of duplicate elements:

- **Allow Duplicates** — `List` and `Queue` types permit identical elements.
- **Require Element Uniqueness** — `Set` types ensure every stored element is distinct.
- **Require Key Uniqueness** — `Map` types enforce uniqueness only for their keys, while allowing associated values to be duplicates.

### 4.3. Access Patterns and Performance

Choosing the right implementation is critical for performance, since different internal structures optimize for different access patterns:

- **Fast Random Access** — `ArrayList` provides the quickest way to retrieve an element by index, ideal for frequent reading or modification by position.
- **Fast End-point Operations** — `ArrayDeque` and `LinkedList` are used when adding or removing elements at the beginning or end, commonly for stacks and queues.
- **Fast Lookups** — `HashSet` and `HashMap` provide the quickest way to check if an element exists or retrieve a value by key.
- **Fast Range Operations** — `TreeSet` and `TreeMap` are used when retrieving a range of data or a subset of elements based on their sorted order.

### 4.4. Thread-Safety and Concurrency

This factor is crucial when multiple threads access the collection simultaneously, since most standard collections aren't thread-safe:

- **Concurrent Classes** — prefer modern classes from the `java.util.concurrent` package (e.g., `ConcurrentHashMap`). These are purpose-built for high-performance, fine-grained concurrency, avoiding a single lock on the entire collection.
- **Synchronized Wrappers** — avoid `Collections.synchronized(...)` unless concurrency needs are very basic and performance isn't critical, since these wrappers lock the entire collection and cause bottlenecks.
- **Raw Synchronization** — avoid explicit `synchronized` blocks around collection access, since it's highly error-prone; prefer specialized concurrent classes instead.
