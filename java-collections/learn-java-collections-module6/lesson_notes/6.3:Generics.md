# Generics: A Quick Primer

## 1. Overview

Generics in Java let us define classes, interfaces, and methods with type parameters, enabling type-safe and more readable code. In any nontrivial software project, bugs are simply a fact of life. Careful planning, programming, and testing can help reduce their pervasiveness, but somehow, somewhere, they'll always find a way to creep into your code. This becomes especially apparent as new features are introduced and your code base grows in size and complexity.

Fortunately, some bugs are easier to detect than others. Compile-time bugs, for example, can be detected early on; we can use the compiler's error messages to figure out what the problem is and fix it right then and there. Runtime bugs, however, can be much more problematic — they don't always surface immediately, and when they do, it may be at a point in the program that is far removed from the actual cause of the problem.

Generics add stability to code by making more bugs detectable at compile time. After completing this lesson, it's worth following up with the [Generics](https://docs.oracle.com/javase/tutorial/extra/generics/index.html) tutorial by Gilad Bracha.

In this lesson, we'll see how generics make collections more robust, how type parameters work, and why raw types should be avoided.

The relevant module we need to import when starting this lesson is: [generics-start](https://github.com/Baeldung/learn-java-collections/tree/module6/generics-start).

If we want to reference the fully implemented lesson, we can import: [generics-end](https://github.com/Baeldung/learn-java-collections/tree/module6/generics-end).

## 2. What Are Generics?

Generics let us write code that works with a variety of types while maintaining compile-time type safety. Without generics, we'd often rely on casting, which can lead to runtime errors if the object is not of the expected type.

With generics, we declare type parameters that tell the compiler what kind of objects a class, interface, or method should work with. The compiler then ensures that only compatible types are used, catching errors before the program runs.

We can introduce generics by declaring a formal type parameter within angle brackets (`<>`).

Let's look at a simple example by declaring a generic class in the `com.baeldung.ljc.domain.model` package, next to the existing `Task` class. Suppose we want a class that holds an object and allows us to retrieve it:

```java
public class Container<T> {
    private T item;

    public Container(T item) {
        this.item = item;
    }

    public T getItem() {
        return item;
    }
}
```

Here, we created a simple generic class named `Container`, where `T` is a type parameter: a placeholder that represents "some type."

Now, when we create an instance, we replace `T` with a concrete type (like `Task` or `String`). Java conventionally uses `T` for type, `E` for elements in collections, `K`/`V` for keys and values in maps, and so on.

The start project ships an empty `JavaCollectionsTests` placeholder under `src/test/java`. Let's use it as the home for the tests in this lesson. We'll start with one that exercises `Container` with a `Task`:

```java
@Test
void givenContainer_whenHoldingTask_thenItemTypeIsTask() {
    Task task = new Task("T001", "Complete Report", "Finish quarterly sales report", LocalDate.of(2025, 7, 15));
    Container<Task> container = new Container<>(task);

    assertEquals("Complete Report", container.getItem().getName());
}
```

The compiler ensures that whatever type we substitute for `T` is used consistently. The `Container` instance we defined is associated with `Task`, so the compiler wouldn't allow passing another type to the constructor, and we can call `getName()` directly on the result of `getItem()` without any casting.

If we intended `Container` to store only `Task` objects, we could have hardcoded it inside the class. However, by using generics, the same class becomes reusable across different types. For example, let's add a test where it holds a `String`:

```java
@Test
void givenContainer_whenHoldingStringType_thenItemTypeIsString() {
    String task = "Review project documentation";
    Container<String> container = new Container<>(task);

    assertEquals("Review project documentation", container.getItem());
}
```

Here, `Container` is holding a `String` value, which demonstrates how generics make the class flexible and reusable for different data types, not just `Task`.

## 3. Using Generics With Collections

Collections are one of the best examples of where generics shine. By parameterizing a collection with a type, we make it type-safe and avoid unnecessary casting.

First, let's write a test that uses a collection without generics:

```java
@Test
void givenTaskListWithoutGenerics_whenRetrieving_thenNeedsCasting() {
    List list = new ArrayList();
    list.add(new Task("T001", "Write tests", "Unit testing", LocalDate.of(2025, 7, 20)));

    Task task = (Task) list.get(0);

    assertEquals("Write tests", task.getName());
}
```

Here, the `get()` method returns an `Object`. We need to cast it to a `Task`. If the object isn't actually a `Task`, this would cause a `ClassCastException` at runtime.

Next, let's write a test that uses generics instead:

```java
@Test
void givenTaskListWithGenerics_whenRetrieving_thenNoCastingNeeded() {
    List<Task> tasks = new ArrayList<>();
    tasks.add(new Task("T002", "Review code", "Peer review", LocalDate.of(2025, 7, 22)));

    Task task = tasks.get(0);

    assertEquals("Review code", task.getName());
}
```

Here, the compiler knows that every element in `tasks` is a `Task`, so no casting is needed.

We can apply this to any collection: for example, `List<String>` represents a list of strings, `Set<Integer>` is a set of integers, and `Map<String, Task>` maps string keys to task values.

Generics enforce these rules at compile time, so many errors are caught early. For instance, if we try to add a number to a `List<String>`, the code won't even compile. We can confirm this directly in a scratch method — uncomment the add call, run `mvn compile`, and observe the error, then re-comment to keep the rest of the suite compilable:

```java
List<String> names = new ArrayList<>();
// names.add(123); // Uncommenting this line causes a compile-time error: incompatible types: int cannot be converted to java.lang.String
```

If we had declared the list as a raw type (without `<String>`), the compiler would have allowed mixed types. However, retrieving values would require casting and could lead to runtime errors.

Here's an example of the danger of raw types:

```java
@Test
void givenRawList_whenAddingDifferentTypes_thenRuntimeErrorLater() {
    List rawList = new ArrayList();
    rawList.add(new Task("T003", "Deploy", "Deploy application", LocalDate.of(2025, 7, 25)));
    rawList.add("Not a task"); // Allowed, but unsafe

    Object obj = rawList.get(1);
    assertThrows(ClassCastException.class, () -> {
        Task wrong = (Task) obj; // Fails at runtime
    });
}
```

In the code above, we added `String` and `Task` types to the `rawList` object. This test compiles fine, but at runtime, the cast fails with a `ClassCastException`.

By enforcing these constraints early, generics make code more robust and maintainable. This is especially important in large projects, where a single incorrect type in a shared collection could break functionality across multiple classes.

## 4. Limitations of Generics in Collections

While generics make collections safer and easier to use, they also come with some limitations.

### 4.1. Type Erasure

In Java, generics are implemented with type erasure. This means the type parameter information is removed during compilation. For example, a `List<Task>` and a `List<String>` are both just a `List` at runtime.

Because of this, generics can't be checked or enforced once the program is running. For instance, we can't use generics to distinguish between parameterized types at runtime, and certain constructs such as arrays of parameterized types (`new List<Task>[]`) aren't allowed:

```java
@Test
void givenGenericLists_whenCheckingTypes_thenTypeErasedAtCompileTime() {
    List<Task> tasks = new ArrayList<>();
    List<String> names = new ArrayList<>();

    assertEquals(tasks.getClass(), names.getClass());
}
```

Even though one list is parameterized with `Task` and the other with `String`, they're both seen as just `ArrayList` when the program runs. The compiler enforces type safety at compile time, but this information isn't preserved in the bytecode.

Type erasure can also make inheritance scenarios and more advanced generic constructs difficult to express. For example, operations that would require precise type information (such as checking a parameterized type with `instanceof`) aren't allowed. In such cases, developers often need to rely on more advanced generic patterns to handle collections safely.

### 4.2. Mixing Raw and Generic Types

As we've seen in the examples above, if we mix raw types with parameterized types, the compiler issues warnings about unchecked operations. This can let the wrong types slip into a collection and cause runtime errors.

By default, `mvn test` only reports a summary unchecked-operation warning. To see the full diagnostic, we run with `-Xlint:unchecked` enabled — for example, `mvn test -Dmaven.compiler.testCompilerArgument=-Xlint:unchecked`. The resulting warning looks like:

```
warning: [unchecked] unchecked call to add(E) as a member of the raw type List
        rawList.add("Not a task");
                   ^
  where E is a type-variable:
    E extends Object declared in interface List
```

The compiler allows this assignment, but attempting to retrieve the element and cast it to a `Task` causes a `ClassCastException` at runtime. This shows why raw types should be avoided altogether.

### 4.3. No Primitive Types

Generics only work with objects, not primitives. For example, we can't have a `List<int>`. Instead, we have to use wrapper classes such as `Integer` and rely on autoboxing.

Let's add a new test method with a quick example of an `Integer` list:

```java
@Test
void givenListOfIntegers_whenAddingPrimitive_thenAutoboxed() {
    List<Integer> numbers = new ArrayList<>();
    numbers.add(42);

    assertEquals(42, numbers.get(0));
}
```

Here, the primitive `int` value is automatically converted to an `Integer` when it's added to the list. This works seamlessly, but it's a reminder that generics operate only on object types.

## 5. Conclusion

Generics make collections safer, clearer, and easier to maintain by catching type errors at compile time and removing the need for casting. They let us express our intent directly, whether that's a list of tasks, a set of unique names, or a map from IDs to objects.

The practical payoff is that we always prefer parameterized collections over raw types: the type information travels with the code, the compiler enforces it, and accidental mixing of types is caught long before a `ClassCastException` would surface at runtime.

## Appendix: Generics in Practice — a Deeper Look

The following material expands on how generics work under the hood, drawing on Oracle's own generics tutorial.

### A.1. Why Use Generics?

Starting with J2SE 5.0, generics were added to the Java language. Generics are Java's mechanism for implementing generic programming — a way to describe data and algorithms that lets us work with different data types without changing the description of the algorithms. Oracle's tutorial on the subject is here: ["Lesson: Generics"](https://docs.oracle.com/javase/tutorial/java/generics/index.html).

The ["Why Use Generics?"](https://docs.oracle.com/javase/tutorial/java/generics/why.html) section of that tutorial highlights two main purposes: stronger type checking at compile time, and elimination of the need for explicit casts.

In a nutshell, generics enable types (classes and interfaces) to be parameters when defining classes, interfaces, and methods. Much like the more familiar formal parameters used in method declarations, type parameters provide a way to reuse the same code with different inputs. The difference is that the inputs to formal parameters are values, while the inputs to type parameters are types.

Code that uses generics has several benefits over non-generic code:

Stronger type checks at compile time — a Java compiler applies strong type checking to generic code and issues errors if the code violates type safety. Fixing compile-time errors is easier than fixing runtime errors, which can be difficult to find.

Elimination of casts — the following code snippet without generics requires casting:

```java
List list = new ArrayList();
list.add("hello");
String s = (String) list.get(0);
```

When rewritten to use generics, the code does not require casting:

```java
List<String> list = new ArrayList<String>();
list.add("hello");
String s = list.get(0);   // no cast
```

Enabling programmers to implement generic algorithms — by using generics, programmers can implement generic algorithms that work on collections of different types, can be customized, and are type safe and easier to read.

### A.2. A Compile-Time Safety Net

Suppose we have the following code:

```java
import java.util.*;
public class HelloWorld {
    public static void main(String []args) {
        List list = new ArrayList();
        list.add("Hello");
        String text = list.get(0) + ", world!";
        System.out.print(text);
    }
}
```

This code runs perfectly well. But suppose we're told "Hello, world!" is an overused phrase and we must return only "Hello". We remove the code that concatenates ", world!". This seems harmless, but we get an error at compile time:

```
error: incompatible types: Object cannot be converted to String
```

The problem is that our `List` stores `Object`s. `String` is a descendant of `Object` (since all Java classes implicitly inherit `Object`), which means we need an explicit cast, but we didn't add one. During the concatenation operation, the static `String.valueOf(obj)` method would have been called using the object, eventually calling the `Object` class's `toString` method.

In other words, our `List` contains an `Object`. Wherever we need a specific type (not `Object`), we have to do the type conversion ourselves:

```java
import java.util.*;
public class HelloWorld {
    public static void main(String []args) {
        List list = new ArrayList();
        list.add("Hello!");
        list.add(123);
        for (Object str : list) {
            System.out.println("-" + (String)str);
        }
    }
}
```

In this case, because `List` takes `Object`s, it can store not only `String`s but also `Integer`s. The worst part is that the compiler doesn't see anything wrong here — the error now surfaces at runtime:

```
java.lang.ClassCastException: java.lang.Integer cannot be cast to java.lang.String
```

This happens because the compiler isn't capable of always correctly guessing the programmer's intent. Java SE 5 introduced generics to let us tell the compiler about our intentions — which types we're going to use.

We fix our code by telling the compiler what we want:

```java
import java.util.*;
public class HelloWorld {
    public static void main(String []args) {
        List<String> list = new ArrayList<>();
        list.add("Hello!");
        list.add(123);
        for (Object str : list) {
            System.out.println("-" + str);
        }
    }
}
```

We no longer need a cast to `String`. In addition, we have angle brackets surrounding the type argument. Now the compiler won't let us compile the class until we remove the line that adds `123` to the list, since this is an `Integer`, and it will tell us so.

Many people call generics "syntactic sugar," and they're right — after generics are compiled, they really do become the same type conversions under the hood. After compilation, all generics are erased. This is called ["type erasure"](https://docs.oracle.com/javase/tutorial/java/generics/erasure.html). Type erasure and generics are designed to be backward compatible with older versions of the JDK, while simultaneously allowing the compiler to help with type definitions in newer versions of Java.

### A.3. Raw Types and the Diamond Operator

Speaking of generics, we always have two categories: parameterized types and raw types.

Raw types are types that omit the "type clarification" in angle brackets. Parameterized types, on the other hand, include a clarification, and can use a special construct added in Java SE 7 called the "[diamond](https://docs.oracle.com/javase/tutorial/java/generics/types.html#diamond)" — so named because the empty angle brackets `<>` form a diamond shape.

The diamond syntax is associated with the concept of ["type inference"](https://docs.oracle.com/javase/tutorial/java/generics/genTypeInference.html). The compiler, seeing `<>` on the right, looks at the left side of the assignment operator to find the type of the variable being assigned, and infers the type on the right from it.

In fact, if a generic type is given on the left but not on the right, the compiler can still infer the type:

```java
import java.util.*;
public class HelloWorld {
    public static void main(String []args) {
        List<String> list = new ArrayList();
        list.add("Hello, World");
        String data = list.get(0);
        System.out.println(data);
    }
}
```

But this mixes the new style with generics and the old style without them, which is highly undesirable. Compiling the code above produces the message:

```
Note: HelloWorld.java uses unchecked or unsafe operations
```

Here's an example of why the diamond matters:

```java
import java.util.*;
public class HelloWorld {
    public static void main(String []args) {
        List<String> list = Arrays.asList("Hello", "World");
        List<Integer> data = new ArrayList(list);
        Integer intNumber = data.get(0);
        System.out.println(data);
    }
}
```

`ArrayList` has a constructor that takes a collection as an argument, and this is where something sinister lies hidden. Without the diamond syntax, the compiler doesn't understand that it's being deceived; with the diamond syntax, it does.

So the rule is: always use the diamond syntax with parameterized types. Otherwise, we risk missing where we're using raw types.

To eliminate "uses unchecked or unsafe operations" warnings, we can use the `@SuppressWarnings("unchecked")` annotation on a method or class — but it's worth thinking carefully before reaching for it. More often than not, it means a type argument is missing rather than that the warning should be silenced.

### A.4. Generic Methods

Generics let us create methods whose parameter types and return type are parameterized. Oracle's tutorial devotes a section to this: ["Generic Methods"](https://docs.oracle.com/javase/tutorial/java/generics/methods.html).

The key syntax to remember: a generic method includes a list of type parameters inside angle brackets, and that list goes before the method's return type.

```java
import java.util.*;
public class HelloWorld {

    public static class Util {
        public static <T> T getValue(Object obj, Class<T> clazz) {
            return (T) obj;
        }
        public static <T> T getValue(Object obj) {
            return (T) obj;
        }
    }

    public static void main(String []args) {
        List list = Arrays.asList("Author", "Book");
        for (Object element : list) {
            String data = Util.getValue(element, String.class);
            System.out.println(data);
            System.out.println(Util.<String>getValue(element));
        }
    }
}
```

The `Util` class has two generic methods. Thanks to type inference, we can either indicate the type directly to the compiler, or specify it ourselves — both options are shown above.

The syntax makes sense once we think about it: when declaring a generic method, we specify the type parameter before the method, because if we declared it after, the JVM wouldn't be able to figure out which type to use. We first declare that we'll use the `T` type parameter, and only then say we're going to return this type.

Naturally, `Util.<Integer>getValue(element, String.class)` fails to compile with: `incompatible types: Class<String> cannot be converted to Class<Integer>`.

When using generic methods, we should always remember type erasure:

```java
import java.util.*;
public class HelloWorld {

    public static class Util {
        public static <T> T getValue(Object obj) {
            return (T) obj;
        }
    }

    public static void main(String []args) {
        List list = Arrays.asList(2, 3);
        for (Object element : list) {
            System.out.println(Util.<Integer>getValue(element) + 1);
        }
    }
}
```

This runs fine, as long as the compiler understands that the return type of the method being called is `Integer`. Replace the console output statement with:

```java
System.out.println(Util.getValue(element) + 1);
```

We get an error:

```
bad operand types for binary operator '+', first type: Object, second type: int.
```

Type erasure has occurred: the compiler sees that no one has specified the type, so the type is treated as `Object`, and the method fails to compile.

### A.5. Generic Classes

Not only methods can be parameterized — classes can too. Oracle's ["Generic Types"](https://docs.oracle.com/javase/tutorial/java/generics/types.html) section covers this. Consider:

```java
public static class SomeType<T> {
    public <E> void test(Collection<E> collection) {
        for (E element : collection) {
            System.out.println(element);
        }
    }
    public void test(List<Integer> collection) {
        for (Integer element : collection) {
            System.out.println(element);
        }
    }
}
```

If we use the generic class, the type parameter is indicated after the class name. Now let's create an instance of this class in a `main` method:

```java
public static void main(String []args) {
    SomeType<String> st = new SomeType<>();
    List<String> list = Arrays.asList("test");
    st.test(list);
}
```

This code runs well — the compiler sees a `List` of `String`s and a `Collection` of `String`s and resolves the call correctly. But if we eliminate the type parameter:

```java
SomeType st = new SomeType();
List<String> list = Arrays.asList("test");
st.test(list);
```

We get an error:

```
java.lang.ClassCastException: java.lang.String cannot be cast to java.lang.Integer
```

This is type erasure again. Since the class no longer uses a type parameter, the compiler decides that, since we passed a `List`, the method with `List<Integer>` is the most applicable overload — and we fail at runtime.

The rule here: if we have a generic class, we should always specify the type parameters.

### A.6. Bounded Type Parameters

We can restrict the types allowed in generic methods and classes. For example, suppose we want a container to accept only a `Number` as the type argument. This feature is described in the [Bounded Type Parameters](https://docs.oracle.com/javase/tutorial/java/generics/bounded.html) section of Oracle's tutorial:

```java
import java.util.*;
public class HelloWorld {

    public static class NumberContainer<T extends Number> {
        private T number;

        public NumberContainer(T number) { this.number = number; }

        public void print() {
            System.out.println(number);
        }
    }

    public static void main(String []args) {
        NumberContainer number1 = new NumberContainer(2L);
        NumberContainer number2 = new NumberContainer(1);
        NumberContainer number3 = new NumberContainer("f"); // fails: String is not a Number
    }
}
```

Here, we've restricted the type parameter to the `Number` class/interface or its descendants. We can also specify not just a class, but interfaces, and even combine multiple bounds:

```java
public static class NumberContainer<T extends Number & Comparable> {
```
