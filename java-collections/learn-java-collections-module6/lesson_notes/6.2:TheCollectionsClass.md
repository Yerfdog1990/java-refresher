## 2. The Collections Class

The Java Collections Framework includes the utility class `java.util.Collections`. This class consists entirely of static methods, which simplify common tasks, including: sorting lists into natural or custom order, reversing the order of elements in a list, searching efficiently within a sorted list, randomizing the order of elements, finding minimum and maximum values, and creating immutable views of collections.

Some of these operations are available directly on collections, but `Collections` often provides simpler or more expressive alternatives. It also includes algorithms (like binary search) that would be cumbersome to reimplement ourselves.

In the following sections, we'll clearly explain these methods and demonstrate how to apply them effectively. As usual, we'll demonstrate the usage of the `Collections` class through unit tests.

## 3. Sorting Lists

Let's review how the `Collections` class provides convenient static methods to sort collections.

Sorting is one of the most common operations on lists. If the element type in the `List` implements `Comparable`, `Collections.sort()` arranges elements into ascending order according to their natural ordering.

For example, we can sort our `stringList` alphabetically:

```java
@Test
void whenSortingWithComparableElements_thenCorrect() {
    Collections.sort(stringList);
    assertEquals(List.of("a", "b", "c", "d", "e"), stringList);
}
```

Here, we initially have an unsorted `stringList`. By calling `Collections.sort()`, we rearrange the string elements in alphabetical order. We verify this result using the `assertEquals()` method, which ensures our sorting works as expected.

If the `List` elements don't implement `Comparable`, or we want to use sorting criteria different from the natural ordering, we can pass a `Comparator` to `Collections.sort()`:

```java
@Test
void whenSortingWithComparator_thenCorrect() {
    Collections.sort(taskList, Comparator.comparing(Task::getDueDate));
    assertEquals(List.of(task01, task02, task03, task04, task05, task06), taskList);
}
```

As the example shows, we passed a `Comparator` to `Collections.sort()` using `Comparator.comparing()` to instruct the `sort()` method to sort each `Task` by its due date.

It's worth noting that `Collections.sort()` does in-place sorting — it arranges the elements in the input `List` directly. If preserving the original order is essential, we should first make a copy of the list and then sort the copy.

## 4. Reversing Lists

Sometimes, we need to reverse the order of elements in a list. The method `Collections.reverse()` lets us do this straightforwardly:

```java
@Test
void whenReversingCollection_thenCorrect() {
    Collections.sort(taskList, Comparator.comparing(Task::getDueDate));
    assertEquals(List.of(task01, task02, task03, task04, task05, task06), taskList);

    Collections.reverse(taskList);
    assertEquals(List.of(task06, task05, task04, task03, task02, task01), taskList);
}
```

In this example, we first sorted our `taskList` by each `Task`'s due date using the `Collections.sort()` method that we just learned. This step is merely for easier verifying the result of `Collections.reverse()`.

As the test method shows, after applying the `reverse()` operation, the ascending-sorted `taskList` becomes a descending-sorted one — the `reverse()` method works as expected.

Similar to the `Collections.sort()` method, the `Collections.reverse()` method also modifies the `List` directly.

## 5. Binary Search in Sorted Lists

The method `Collections.binarySearch()` allows us to quickly find the position of an element in a sorted `List`. The algorithm works by repeatedly dividing the `List` in half until the element is found or until the search space is empty. Because of this divide-and-conquer approach, it locates elements much faster than scanning through the entire list.

Next, let's create a test to binary-search a task in `taskList`:

```java
@Test
void whenBinarySearchInSortedTasks_thenCorrect() {
    Collections.sort(taskList, Comparator.comparing(Task::getDueDate));
    int task04Index = Collections.binarySearch(taskList, task04, Comparator.comparing(Task::getDueDate));
    assertEquals(3, task04Index);
}
```

As the test shows, we need to provide the list, the target element, and the same comparator used for sorting, and we obtain the element's index.

Now let's see what happens with a list of elements sorted by their natural order, and when we search for a non-existing element:

```java
@Test
void whenBinarySearchForString_thenNoComparatorNeededAndNonExistingRetrievesNegativeInsertingOrderLessOne() {
    List<String> sortedStringList = new ArrayList<>(List.of("a", "b", "d", "e"));

    int indexOfD = Collections.binarySearch(sortedStringList, "d");
    assertEquals(2, indexOfD);

    int nonExistingIndex = Collections.binarySearch(sortedStringList, "c");
    assertEquals(-3, nonExistingIndex);

    sortedStringList.add(-nonExistingIndex - 1, "c");
    assertEquals(List.of("a", "b", "c", "d", "e"), sortedStringList);
}
```

As we can see, if the elements implement `Comparable` and are sorted by their natural order, no comparator is needed.

When the element isn't found, `binarySearch()` returns a negative value equal to `-(insertion point) - 1`. This lets us know where the element would be inserted to keep the list sorted, which is exactly what `-result - 1` recovers in the snippet above.

It's important to remember that binary search only works correctly on sorted lists. If the list isn't sorted, the result is unpredictable.

For other `Collection` types, there are some important notes:

With a `Set` such as `HashSet` or `LinkedHashSet`, binary search cannot be applied directly, since sets don't guarantee index-based access or sorting. If we need to search, we must first convert the set into a sorted list. With a `SortedSet` such as `TreeSet`, searching is built into the set API itself through methods such as `contains()`, `floor()`, and `ceiling()`, which use the tree structure internally instead of binary search. For `Map`s, binary search doesn't apply directly — instead, we usually use methods on `NavigableMap`, such as `floorEntry()` or `ceilingEntry()`, for key-based lookups.

## 6. Shuffling Lists

The method `Collections.shuffle()` randomly rearranges elements in a `List`. This method is especially useful when we want random order, such as in randomized tests or card shuffling simulations.

Next, let's create a test method to randomize our `taskList` using `Collections.shuffle()`:

```java
@Test
void whenShufflingCollection_thenCorrect() {
    Collections.sort(taskList, Comparator.comparing(Task::getDueDate));
    assertEquals(List.of(task01, task02, task03, task04, task05, task06), taskList);

    System.out.println("Shuffling the list:");
    Collections.shuffle(taskList);
    System.out.println(taskList);

    System.out.println("=========================");
    System.out.println("Shuffling the list again:");
    Collections.shuffle(taskList);
    System.out.println(taskList);
}
```

Again, to verify the shuffling result more easily, we first sorted our `taskList`. If we run this test, we'll get something like this:

```
Shuffling the list:
[Task [code=T06, ...dueDate=2025-06-01], Task [code=T01, ...dueDate=2025-01-01], Task [code=T03, ...dueDate=2025-03-01], Task [code=T04, ...dueDate=2025-04-01], Task [code=T05, ...dueDate=2025-05-01], Task [code=T02, ...dueDate=2025-02-01]]

Shuffling the list again:
[Task [code=T02, ...dueDate=2025-02-01], Task [code=T04, ...dueDate=2025-04-01], Task [code=T03, ...dueDate=2025-03-01], Task [code=T06, ...dueDate=2025-06-01], Task [code=T05, ...dueDate=2025-05-01], Task [code=T01, ...dueDate=2025-01-01]]
```

In this example, we called `Collections.shuffle()` twice, and it turns out that every time we call it, the elements in `taskList` are rearranged.

The key takeaway is that shuffling preserves all elements but randomizes their order. Each run can produce a different sequence, making it ideal for testing, sampling, or game-like scenarios.

## 7. Filling Lists

The method `Collections.fill()` replaces every element of the `List` with a specified value. This can be useful when initializing or resetting lists using a predefined template element.

Next, let's create a new test method to replace all elements in our `taskList` with a new `Task` object using the `fill()` method:

```java
@Test
void whenFillingCollections_thenCorrect() {
    assertEquals(6, taskList.size());

    Task templateTask = new Task("T00", "{TemplateTaskName}", "This is template Task", null);
    Collections.fill(taskList, templateTask);

    assertEquals(6, taskList.size());
    assertEquals(List.of(templateTask, templateTask, templateTask, templateTask, templateTask, templateTask), taskList);
}
```

Here, we're using a `templateTask` as the replacement for all existing elements.

The assertions verify that `taskList` keeps the same size, but that all elements now reference the same object instance, `templateTask`.

It's worth pointing out that since `Collections.fill()` replaces elements with the same reference, changing the template object afterward will affect every position in the list.

## 8. Finding Minimum and Maximum in Collections

The methods `Collections.min()` and `Collections.max()` allow us to find the smallest and largest elements in a collection quickly.

Similar to `Collections.sort()`, if the elements implement `Comparable`, the methods can determine the minimum or maximum directly. Otherwise, we can pass a `Comparator` to define how the minimum and maximum should be determined.

Next, let's use these two methods to find the minimum and maximum elements from our `stringList` and `taskList`:

```java
@Test
void whenFindingMinAndMax_thenCorrect() {
    Task minTask = Collections.min(taskList, Comparator.comparing(Task::getDueDate));
    Task maxTask = Collections.max(taskList, Comparator.comparing(Task::getDueDate));
    assertEquals(task01, minTask);
    assertEquals(task06, maxTask);

    String minString = Collections.min(stringList);
    String maxString = Collections.max(stringList);
    assertEquals("a", minString);
    assertEquals("e", maxString);
}
```

As the test shows, these methods returned the expected elements.

## 9. Creating Empty Collections

The `Collections` class includes methods for creating immutable empty collections: `Collections.emptyList()`, `Collections.emptySet()`, and `Collections.emptyMap()`.

These methods return empty, read-only collections of the given type. They are useful when we need to return a safe placeholder collection instead of returning `null`:

```java
@Test
void whenCreatingEmptyCollections_thenCorrect() {
    List<String> emptyList = Collections.emptyList();
    assertTrue(emptyList.isEmpty());

    Map<String, String> emptyMap = Collections.emptyMap();
    assertTrue(emptyMap.isEmpty());

    Set<Task> emptySet = Collections.emptySet();
    assertTrue(emptySet.isEmpty());

    assertThrows(UnsupportedOperationException.class, () -> emptyList.add("a"));
}
```

It's important to note that these empty collections are all immutable. As the test shows, if we try to modify the empty collections, an `UnsupportedOperationException` will be thrown.

## 10. Creating Unmodifiable Collections

The `Collections` class provides a family of unmodifiable methods, such as `unmodifiableList()` and `unmodifiableSet()`, to return read-only views of the input `Collection`. Any attempt to modify a read-only view throws an exception. This is useful when we want to share data safely without risking accidental changes.

Next, let's take `unmodifiableList()` as an example to demonstrate how to use it in practice:

```java
@Test
void whenCreatingUnmodifiableCollections_thenCorrect() {
    List<Task> unmodifiableTaskList = Collections.unmodifiableList(taskList);
    assertEquals(6, unmodifiableTaskList.size());

    assertThrows(UnsupportedOperationException.class, () -> unmodifiableTaskList.add(task01));
    assertThrows(UnsupportedOperationException.class, () -> Collections.sort(unmodifiableTaskList, Comparator.comparing(Task::getDueDate)));
}
```

In this example, attempting to modify (adding an element and in-place sorting) the unmodifiable `List` throws an `UnsupportedOperationException`.
