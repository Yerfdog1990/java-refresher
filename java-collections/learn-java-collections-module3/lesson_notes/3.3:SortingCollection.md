# Sorting Collections with Comparable and Comparator 

## 1. Overview

## 2. Understanding Natural Ordering With `Comparable`

The `Comparable` interface defines the **natural ordering** of objects. A class implementing it defines the **`compareTo()`** method, specifying how objects are ordered relative to each other.

`compareTo()` returns an `int`:

- **Negative** — the current object comes **before** the specified object.
- **Zero** — they are equal in sort order (and ideally equal in general).
- **Positive** — the current object comes **after** the specified object.

Natural ordering for `Task` based on `dueDate`:

```java
public class Task implements Comparable<Task> {
    // ...
    @Override
    public int compareTo(Task otherTask) {
        return this.dueDate.compareTo(otherTask.getDueDate());
    }
}
```

`LocalDate` already implements `Comparable`, so we **delegate** to its `compareTo()`. This makes the logic concise: we rely on the natural order of a single field (`dueDate`, ascending) to order the whole `Task`. For multiple fields or more complex logic, expand `compareTo()` accordingly.

Test setup and comparison:

```java
@BeforeEach
void setUp() {
    tasks = new ArrayList<>(List.of(
      new Task("T001", "A- Past Task", "Due date in far past", LocalDate.of(2000, 4, 15)),
      new Task("T002", "B- Far-Future Task", "Due date in far future", LocalDate.of(2070, 5, 10)),
      new Task("T003", "C- Mid-Future Task", "Due date in near future", LocalDate.of(2050, 12, 1))
    ));
}

@Test
void whenComparingTasks_thenOlderDueDateComesFirst() {
    Task pastDueTask = tasks.get(0);
    Task futureDueTask = tasks.get(1);
    int result = pastDueTask.compareTo(futureDueTask);
    assertTrue(result < 0);
}
```

The result is negative, as expected (past date comes first).

### 2.1. Consistency with `equals()`

Though not required by the language, the Java docs **strongly recommend** that `compareTo()` be **consistent with `equals()`**:

- If `a.equals(b)` is `true`, then `a.compareTo(b)` should return `0`.
- This keeps ordering-equality aligned with object-equality.

This matters for sorted structures like **`TreeSet`** and **`TreeMap`**, which rely **solely** on `compareTo()` (or a `Comparator`) to store and retrieve elements. If inconsistent, they can misbehave — failing to find elements, misplacing them, or silently discarding "distinct" objects.

> The lesson's example doesn't follow this recommendation, for simplicity, since it doesn't use those collections. The same recommendation applies to custom `Comparator` instances.

## 3. Sorting Collections Using Natural Ordering

`Collections.sort()` sorts a list by its elements' natural ordering (`Comparable`):

```java
@Test
void whenUsingNaturalOrdering_thenSortTasksByDueDateAscending() {
    Collections.sort(tasks);
    assertEquals("A- Past Task", tasks.get(0).getName());
    assertEquals("C- Mid-Future Task", tasks.get(1).getName());
    assertEquals("B- Far-Future Task", tasks.get(2).getName());
}
```

Result: past due date first, then nearer future, then farthest future.

## 4. The `Comparator` Interface

While `Comparable` defines ordering **within** the object, `Comparator` defines sorting criteria **externally**, without modifying the original class. Its primary method is **`compare(a, b)`**, which returns an `int` with the same sign convention as `compareTo()`.

Rules of thumb:

- Use **`Comparable`** for a single, natural ordering inherent to the class.
- Use **`Comparator`** for multiple, context-specific sorting strategies.
- Use **`Comparator`** when you don't control the class definition (e.g. sorting `String` by length).

## 5. Sorting Collections With a Custom `Comparator`

Use a custom `Comparator` when objects don't implement `Comparable`, or when you need a criterion other than the natural ordering.

Sort tasks alphabetically by name (anonymous class):

```java
@Test
void whenUsingCustomComparator_thenSortTasksByName() {
    Comparator<Task> nameComparator = new Comparator<>() {
        @Override
        public int compare(Task task1, Task task2) {
            return task1.getName()
                .compareTo(task2.getName());
        }
    };
    tasks.sort(nameComparator);
    assertEquals("A- Past Task", tasks.get(0).getName());
    assertEquals("B- Far-Future Task", tasks.get(1).getName());
    assertEquals("C- Mid-Future Task", tasks.get(2).getName());
}
```

We rely on `String`'s natural ordering for names. `tasks.sort(nameComparator)` and `Collections.sort(tasks, nameComparator)` are interchangeable.

### 5.1. Custom Comparators With Lambda Expressions

`Comparator` is a **functional interface**, so a lambda is more concise:

```java
@Test
void whenUsingLambdaComparator_thenSortTasksByName() {
    tasks.sort((t1, t2) -> t1.getName().compareTo(t2.getName()));
    assertEquals("A- Past Task", tasks.get(0).getName());
    assertEquals("B- Far-Future Task", tasks.get(1).getName());
    assertEquals("C- Mid-Future Task", tasks.get(2).getName());
}
```

The entire comparison fits on one line.

### 5.2. Built-in Comparator Helper Methods

Java's fluent `Comparator` API supports field extraction, chaining, and ordering behavior. The common starting point is **`Comparator.comparing()`**, built from any field getter; from there you can `reversed()`, add tie-breakers with **`thenComparing()`**, rely on natural order, or handle nulls:

```java
@Test
void whenBuildingComparatorUsingHelperMethods_thenSortTasksByNameAndCodeReversed() {
    tasks.add(new Task(
      "T004", "B- Far-Future Task", "Due date even further in the future", LocalDate.of(2080, 5, 10)));
    Comparator<Task> comparator = Comparator.comparing(Task::getName)
        .thenComparing(Task::getCode)
        .reversed();
    Collections.sort(tasks, comparator);
    assertEquals("C- Mid-Future Task", tasks.get(0).getName());
    assertEquals("Due date even further in the future", tasks.get(1).getDescription());
    assertEquals("Due date in far future", tasks.get(2).getDescription());
    assertEquals("A- Past Task", tasks.get(3).getName());
}
```

This compares first by name, breaks ties by `code` via `thenComparing()`, then reverses the whole ordering with `reversed()`.

> Common helpers: `Comparator.comparing(keyExtractor)`, `comparingInt/comparingLong/comparingDouble` (avoid autoboxing), `thenComparing(...)`, `reversed()`, `nullsFirst(...)` / `nullsLast(...)`, and `naturalOrder()` / `reverseOrder()`.

## 6. Side-by-Side Comparison: Comparable vs. Comparator

| Feature | `Comparable` | `Comparator` |
|---|---|---|
| Defined within a class? | Yes | No — external to the class |
| Multiple strategies? | No — one natural ordering | Yes — unlimited |
| Method to implement | `compareTo(other)` | `compare(o1, o2)` |
| Best suited for | Default natural ordering | Flexible custom sorting |

---

## 7. Conclusion

`Comparable` defines a single natural ordering inside the class via `compareTo()`, sorted with `Collections.sort()`. `Comparator` defines flexible, external sorting strategies via `compare()` — expressible as anonymous classes, lambdas, or the fluent `Comparator.comparing().thenComparing().reversed()` API. Keeping `compareTo()`/`compare()` consistent with `equals()` matters especially for `TreeSet` and `TreeMap`. Together these tools cover a wide range of sorting scenarios.
