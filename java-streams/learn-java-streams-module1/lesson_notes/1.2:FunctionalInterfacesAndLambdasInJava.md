## 1. Overview

Java's support for functional-style programming starts with two essential features: **functional interfaces** and **lambda expressions**. Together they let us express behavior as values and pass it around with minimal boilerplate — a pattern that's especially powerful with the Streams API.

This lesson covers: what functional interfaces are, the most common built-in ones in `java.util.function`, implementing them via anonymous inner classes, simplifying with lambda expressions, method references, and a first look at how these concepts connect to streams. These are foundational tools for the rest of the Streams API work ahead.

## 2. Introduction to Functional Interfaces

A **functional interface** is any interface that declares exactly one abstract method. It represents a single unit of behavior and is the target type for lambda expressions and method references.

Java has had functional interfaces since early days — `Runnable`, `Comparator`. Java 8 introduced a full, standardized set in the `java.util.function` package, which is the focus of this lesson.

## 3. Built-in Functional Interfaces in `java.util.function`

Implemented first via anonymous inner classes, to appreciate the difference lambdas make later.

### Aside: what is an anonymous class?

An **anonymous class** is a class that:

- has no name,
- is declared and instantiated in a single expression,
- is typically used for a one-time implementation of an interface or superclass,
- avoids creating a separate `.java` file for a class that will only be used once.

**Traditional approach — a named class.** Implementing `Function<String, Integer>` the long way:

```java
import java.util.function.Function;

class StringLengthFunction implements Function<String, Integer> {
    @Override
    public Integer apply(String s) {
        return s.length();
    }
}

public class Main {
    public static void main(String[] args) {
        Function<String, Integer> strLength = new StringLengthFunction();
        System.out.println(strLength.apply("Baeldung")); // 8
    }
}
```

This works, but creating a whole class just to implement one method feels excessive.

**Anonymous class version** — same result, no separate class:

```java
Function<String, Integer> strLength = new Function<>() {
    @Override
    public Integer apply(String s) {
        return s.length();
    }
};
```

Under the hood, the compiler generates something equivalent to the named-class version and instantiates it directly — but that generated class is never something we write ourselves:

```java
class AnonymousFunction implements Function<String, Integer> {
    @Override
    public Integer apply(String s) {
        return s.length();
    }
}
Function<String, Integer> strLength = new AnonymousFunction();
```

**Why this compiles.** `Function<T, R>` is itself a functional interface with a single abstract method:

```java
@FunctionalInterface
public interface Function<T, R> {
    R apply(T t);
}
```

`Function<String, Integer>` fixes `T = String` and `R = Integer`, so the method to implement must be `Integer apply(String s)`. Because there's exactly one abstract method, Java lets us provide an implementation via a named class, an anonymous class, *or* a lambda expression.

**"Behavior as an object."** Ordinarily a variable stores data (`String name = "John";`). Here, the variable stores *behavior* — executable code:

```java
Function<String, Integer> strLength = s -> s.length();
```

That behavior can then be passed around like any value:

```java
public static void process(String text, Function<String, Integer> func) {
    System.out.println(func.apply(text));
}

process("Baeldung", s -> s.length()); // 8
```

`process` doesn't know *how* the transformation works — it just receives an object that knows how to perform it. This is one of the foundations of functional programming in Java.

**Anonymous class vs. lambda.**

| Anonymous class | Lambda |
|---|---|
| Creates an (unnamed) class object | Creates a function-like implementation |
| More verbose | More concise |
| Can have fields and multiple methods; works with any interface or abstract class | Only implements the single functional method; only works for functional interfaces |
| Has its own `this` reference | `this` refers to the enclosing class |
| Predates Java 8 | Introduced in Java 8 |

```java
// Anonymous class
Function<String, Integer> f = new Function<>() {
    @Override
    public Integer apply(String s) {
        return s.length();
    }
};

// Lambda — same result, preferred when available
Function<String, Integer> f = s -> s.length();
```

**Other classic uses of anonymous classes** — common before Java 8 introduced lambdas:

```java
// Comparator
Comparator<Person> comparator = new Comparator<Person>() {
    @Override
    public int compare(Person a, Person b) {
        return a.age - b.age;
    }
};
Collections.sort(people, comparator);

// Runnable
Runnable task = new Runnable() {
    @Override
    public void run() {
        System.out.println("Thread running");
    }
};
new Thread(task).start();

// Swing event listener
button.addActionListener(new ActionListener() {
    @Override
    public void actionPerformed(ActionEvent e) {
        System.out.println("Button clicked");
    }
});
```

**Why it's still worth knowing both.** Many older, pre-Java-8 libraries lean heavily on anonymous classes, while modern codebases prefer lambdas for functional interfaces — so recognizing both forms matters when reading real-world Java code.

### 3.1. `Function<T, R>`

Represents a transformation from one value to another, potentially of a different type.

```java
Function<String, Integer> strLength = new Function<>() {
    @Override
    public Integer apply(String s) {
        return s.length();
    }
};
assertEquals(8, strLength.apply("Baeldung"));
```

Even though `Function` is just an interface, an anonymous class gives an inline implementation of its single abstract method — no separate named class needed. This is treating behavior as an object that can be passed around.

### 3.2. `BiFunction<T, U, R>`

Same idea, but takes two input values.

```java
BiFunction<Integer, Integer, Double> divideToDouble = new BiFunction<>() {
    @Override
    public Double apply(Integer i1, Integer i2) {
        return i1.doubleValue() / i2.doubleValue();
    }
};
assertEquals(2.0, divideToDouble.apply(4, 2));
```

### 3.3. `Consumer<T>`

Operates on a single input and returns nothing.

```java
Consumer<String> printString = new Consumer<>() {
    @Override
    public void accept(String s) {
        System.out.println(s);
    }
};
printString.accept("Hello Baeldung");
```

Used here to print a string as a side effect.

### 3.4. `Supplier<T>`

Produces a value without taking any input.

```java
Supplier<String> idGenerator = new Supplier<>() {
    @Override
    public String get() {
        return UUID.randomUUID().toString();
    }
};
assertTrue(idGenerator.get().length() > 0);
```

### 3.5. `Predicate<T>`

Evaluates a condition and returns a boolean.

```java
Predicate<Integer> isEven = new Predicate<>() {
    @Override
    public boolean test(Integer i) {
        return i % 2 == 0;
    }
};
assertTrue(isEven.test(4));
```

### 3.6. Beyond the Core Built-ins

Java also provides more specialized functional interfaces: `UnaryOperator`, `BinaryOperator`, `IntPredicate`, and others.

If no built-in type fits, we can define a custom functional interface — as long as it declares exactly one abstract method. It's recommended to annotate it with `@FunctionalInterface`: this signals intent to readers and lets the compiler catch mistakes such as accidentally adding a second abstract method.

## 4. Lambda Expression Syntax

Anonymous inner classes work, but the syntax is verbose and doesn't chain well, especially in streams. **Lambda expressions** offer a compact way to provide the implementation of a functional interface — shorthand for creating an instance of a functional interface without writing an anonymous class.

Basic syntax:

```
(parameters) -> expression
```

- `parameters` — a comma-separated list of inputs.
- `->` — the arrow token, separating input from the function body.
- `expression` — the body of the function.

## 5. Built-in Functional Interfaces as Lambda Expressions

Any functional interface — including the built-in ones — can be represented as a lambda.

```java
@Test
void givenFunctionalInterfacesAsLambdas_whenExecutingThem_thenAllReturnCorrectResult() {
    Supplier<String> idGenerator = () -> UUID.randomUUID().toString();

    Function<String, Integer> strLength = s -> s.length();

    BiFunction<Integer, Integer, Double> divideToDouble = (s1, s2) -> s1.doubleValue() / s2.doubleValue();

    Consumer<String> printString = s -> System.out.println(s);

    Predicate<Integer> isEven = s -> s % 2 == 0;
}
```

Rather than verbose anonymous classes, behavior is passed using short inline functions — a key technique for Stream operations later in the course.

**Underlying mechanism:** lambdas aren't fundamentally new. They compile down to instances of functional interfaces, just like anonymous inner classes, but with a more efficient, lightweight representation under the hood. This means lambdas integrate seamlessly with Java's object-oriented model while offering more concise syntax, and it also explains runtime behavior, performance characteristics, and limitations.

## 6. Lambda Expression Parameters

Lambdas can reference variables from the surrounding scope (e.g. a common prefix/suffix in output) — but only if those variables are **effectively final**, i.e. assigned once and never reassigned. Reassigning such a variable later, inside or outside the lambda, is a compile-time error.

```java
@Test
void givenTask_whenBuildingDueYearSummary_thenSummaryConstructed() {
    String summaryConnector = "is due on";

    // Uncommenting the next line would break the lambda below:
    // summaryConnector = "changed connector"; // Compile-time error: not effectively final

    Task t1 = new Task("T1", "Task Name", "Task Description", LocalDate.of(2050, 1, 1));

    Function<Task, String> dueYearSummary = task -> {
        final String name = task.getName();
        final int dueYear = task.getDueDate().getYear();
        return "%s %s %s".formatted(name, summaryConnector, dueYear);
    };

    String summaryValue = dueYearSummary.apply(t1);

    assertEquals("Task Name is due on 2050", summaryValue);
}
```

When a lambda body needs more than one statement, wrap it in braces and use an explicit `return` if it produces a result — keeps the code structured while still benefiting from lambda syntax.

**Type inference:** Java infers types within lambda expressions.

- The type of `task` wasn't declared — the compiler infers it from the `Function<Task, String>` declaration.
- The return type wasn't specified explicitly — the compiler expects a `String` based on the functional interface, and checks the lambda body matches.

## 7. Method References

A **method reference** is shorthand for a lambda that simply calls an existing method. It uses the double-colon (`::`) operator:

- Static method — `ClassName::staticMethod`
- Instance method of a particular object — `instance::method`
- Instance method of an arbitrary object of a particular type — `ClassName::instanceMethod`
- Constructor reference — `ClassName::new`

Method references improve readability when a lambda body does nothing more than delegate to another method.

```java
@Test
void givenAList_whenUsingMethodReference_thenGetResult() {
    Function<Task, LocalDate> getDueDate = task -> task.getDueDate();
    Function<Task, LocalDate> getDueDateRef = Task::getDueDate;

    Task t1 = new Task("T2", "Task 2 Name", "Task 2 Description", LocalDate.of(2050, 1, 1));
    LocalDate dueDate = getDueDate.apply(t1);
    LocalDate dueDateRef = getDueDateRef.apply(t1);

    assertEquals(dueDate, dueDateRef);
}
```

Like a lambda, a method reference creates an instance of a functional interface — everything learned about target types, type inference, and captured variables still applies.

## 8. Functional Interfaces, Lambdas, and the Streams API

A preview of how streams and lambdas work together, using a small list of tasks:

```java
private final List<Task> tasks = List.of(
    new Task("T1", "Task 1", "Task 1", LocalDate.now()),
    new Task("T2", "Task 2", "Task 2", LocalDate.now()),
    new Task("T3", "Task 3", "Task 3", LocalDate.now()),
    new Task("S1", "Task 4", "Task 4", LocalDate.now())
);

@Test
void givenListOfTasks_whenJoiningCodesUsingStream_thenCorrectStringIsReturned() {
    String combinedCodes = tasks.stream()
        .map(Task::getCode)
        .filter(code -> code.startsWith("T"))
        .collect(Collectors.joining(", "));

    assertEquals("T1, T2, T3", combinedCodes);
}
```

Typing `tasks.stream().` in an IDE like IntelliJ or Eclipse triggers auto-completion suggesting many `Stream` operations that expect functional interfaces as arguments.

In this example, each pipeline step's behavior is expressed concisely with lambdas and method references:

- First, all task codes are extracted with a `Function`, represented by the `Task::getCode` method reference.
- Then, only codes starting with `"T"` are kept using a `Predicate` defined as a lambda expression.

### Aside: what does `.map(Task::getCode)` actually do?

`map()` **transforms** each element in the stream into something else. Think of it as: take each object → apply a transformation → produce a new stream.

Given:

```java
List<Task> tasks = List.of(
    new Task("T001"),
    new Task("T002"),
    new Task("T003")
);
```

each element starts out as a `Task`. Calling `.map(Task::getCode)` invokes `getCode()` on every element:

```
Task("T001") ──getCode()──> "T001"
Task("T002") ──getCode()──> "T002"
Task("T003") ──getCode()──> "T003"
```

So the stream's element type changes from `Stream<Task>` to `Stream<String>`.

**`Task::getCode` is a method reference** — shorthand for `task -> task.getCode()`. These two are equivalent:

```java
.map(Task::getCode)
.map(task -> task.getCode())
```

Both read as: "for every `task` in the stream, call `getCode()` and use the result."

**Why it's called `map`.** It maps one type of value to another — `Task → String` here. Other examples: `.map(String::length)` maps `String → Integer`; `.map(Person::getName)` maps `Person → String`; `.map(Student::getAge)` maps `Student → Integer`.

This ties directly back to `Function<T, R>`: `map()` accepts a `Function`, and `Task::getCode` is effectively supplying a `Function<Task, String>` that describes `Task → String`. Importantly, `map()` does **not** modify the original `Task` objects — it produces a new stream of transformed values.

**Does a stream always need a `map()`?** No — `map()` is just one of many stream operations, and it's entirely optional. A few others:

- `filter(Predicate)` — selects elements; the type stays the same (`Stream<Task> → Stream<Task>`), but some elements may be dropped.
- `sorted()` — orders elements (`Stream<Task> → Stream<Task>`).
- `forEach(Consumer)` — does something with each element (a terminal operation, no return value).
- `collect(Collector)` — turns the stream into a collection or other result, e.g. `Collectors.toList()`.

For example, this pipeline has no `map()` at all:

```java
tasks.stream()
     .filter(task -> task.getPriority() > 5)
     .forEach(System.out::println);
```

Stream operations fall into two categories:

- **Intermediate operations** — return another stream, so they can be chained: `filter()`, `map()`, `sorted()`, `distinct()`, `limit()`.
- **Terminal operations** — end the pipeline and produce a result or side effect: `collect()`, `forEach()`, `count()`, `reduce()`, `findFirst()`, `anyMatch()`.

A useful rule of thumb: a stream pipeline usually has zero or more intermediate operations followed by exactly one terminal operation — `map()` is one option among several, never a requirement.

## 9. Conclusion

Functional interfaces, anonymous inner classes, lambda expressions, and method references together bring functional-style programming to Java. They give a clean, expressive way to pass behavior as a value — a technique relied on extensively when working with streams throughout the rest of the course.
