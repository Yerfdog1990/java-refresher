## 1. Overview

Introduces the functional programming style in Java and how the Streams API embraces it. Compares imperative loops with stream pipelines, explains why streams are often clearer and faster, and flags the main pitfalls when moving away from classic collection processing.

## 2. Functional Programming Basics

Functional programming treats **behavior as data** — instead of describing *how* to iterate over a collection, we describe *what* operation to apply.

Two Java 8 features enabled this:

- **Lambda expressions** — write functions inline.
- **Functional interfaces** — single-method interfaces used as lambda targets, letting functional style integrate with Java's OO structure (covered in more detail in later lessons).

Because functions became first-class citizens, they can be passed around like any other value, composed, and fed into stream operations.

### Aside: what does "first-class citizen" mean?

A **first-class citizen** in programming is a value or entity that can do everything basic data types like numbers or strings can do: you can store it in a variable, pass it into a function, return it from a function, and put it in a data structure.

What first-class citizens can do:

- **Store in variables** — assign a function to a name just like a number.
- **Pass as arguments** — send a function into another function as input.
- **Return from functions** — create and give back a new function.
- **Put in data collections** — store functions inside lists, arrays, or maps.

Why it matters for functions:

- **Better code reuse** — write generic logic and plug in custom behavior.
- **Clean data processing** — chain stream operations like `map`, `filter`, and `reduce`.
- **Less boilerplate** — skip writing separate named helper functions for simple tasks.

In Java, functions became first-class citizens in Java 8 through lambda expressions and functional interfaces — this lets us treat behavior as data, passing methods around just like integers or strings. The example below stores, passes, returns, and streams a function:

```java
import java.util.List;
import java.util.Arrays;
import java.util.function.Function;
import java.util.stream.Collectors;

public class FirstClassFunctions {
    public static void main(String[] args) {
        // 1. Store a function in a variable
        // This function takes a String and returns its uppercase version
        Function<String, String> uppercaseFn = (str) -> str.toUpperCase();

        // 2. Pass a function as an argument
        // We pass the 'uppercaseFn' variable into our custom method
        String lowerName = "java";
        String processedName = modifyString(lowerName, uppercaseFn);
        System.out.println(processedName); // Outputs: JAVA

        // 3. Return a function from another method
        // We get a new function dynamically and apply it
        Function<String, String> secretFn = getSecretFunction();
        System.out.println(secretFn.apply("hello")); // Outputs: hello!!!

        // 4. Feed functions into stream operations
        // Functions like 'map' accept behavior to process collections seamlessly
        List<String> frameworks = Arrays.asList("spring", "hibernate", "struts");
        List<String> loudFrameworks = frameworks.stream()
                .map(uppercaseFn) // Passing the function directly to the stream
                .collect(Collectors.toList());

        System.out.println(loudFrameworks); // Outputs: [SPRING, HIBERNATE, STRUTS]
    }

    // Helper method that accepts a function as a parameter
    public static String modifyString(String input, Function<String, String> processor) {
        return processor.apply(input);
    }

    // Helper method that returns a function
    public static Function<String, String> getSecretFunction() {
        return (text) -> text + "!!!";
    }
}
```

Core components used:

- `Function<T, R>` — a built-in functional interface representing a function that accepts one argument of type `T` and produces a result of type `R`.
- Lambda expression `(str) -> str.toUpperCase()` — the actual anonymous function block being assigned and passed around.
- `Stream.map()` — a pipeline tool that requires passing in a function to transform data elements.

Core idea: avoid shared, mutable state. Prefer **pure functions** — functions that:

- depend only on their inputs,
- return new values,
- don't modify anything outside their own scope.

In short, pure functions avoid side effects: they don't alter external variables, perform I/O, or touch shared data.

## 3. Why Use Streams

Example from `JavaStreamsUnitTest`. Imperative version — filters task codes starting with `"T"` and joins them:

```java
String joinCodesImperatively(List<Task> tasks) {
    List<String> codes = new ArrayList<>();
    tasks.forEach(t -> {
        if (t.getCode().startsWith("T")) {
            codes.add(t.getCode());
        }
    });
    return String.join(", ", codes);
}
```

Test data and check:

```java
private final List<Task> tasks = List.of(
    new Task("T1", "Task 1", "Task 1", LocalDate.now()),
    new Task("T2", "Task 2", "Task 2", LocalDate.now()),
    new Task("T3", "Task 3", "Task 3", LocalDate.now()),
    new Task("S1", "Task 4", "Task 4", LocalDate.now())
);

@Test
void givenListOfTasks_whenJoiningCodesUsingImperative_thenCorrectStringIsReturned() {
    String combinedCodes = joinCodesImperatively(tasks);
    assertEquals("T1, T2, T3", combinedCodes);
}
```

**Problem:** the imperative version mixes *what* we want (filter, map, join) with *how* we get it (looping, building a result list).

Stream version — same result, expressed as a pipeline:

```java
String joinCodesWithStream(List<Task> tasks) {
    return tasks.stream()
      .map(Task::getCode)
      .filter(code -> code.startsWith("T"))
      .collect(Collectors.joining(", "));
}
```

Reads as a data flow: take the stream → transform each element → filter by code → collect the result. Iteration details and buffering are hidden behind descriptive operations.

Equivalence test:

```java
@Test
void givenListOfTasks_whenJoiningCodesUsingStream_thenGetTheSameAsIterativeApproach() {
    assertEquals(joinCodesWithStream(tasks), joinCodesImperatively(tasks));
}
```

## 4. Advantages of Streams

- **Readable / declarative style** — pipeline focuses on domain verbs (`filter()`, `map()`, `collect()`), leaving iteration mechanics to the framework. More expressive, less noise, shorter methods, intent is clear at a glance.
- **Lazy evaluation and performance** — pipeline steps aren't executed immediately; they run only when a final (terminal) result is needed. Avoids unnecessary work and can improve performance.
- **Easy parallelization** — because stream operations are designed to be stateless, `parallelStream()` can often be swapped in to process elements simultaneously and use more of the system's processing resources.
- **Separation of concerns** — transformation logic (lambdas) is separated from iteration details; the framework handles traversal and collection.
- **Composable operations** — simple steps like `filter()` and `map()` chain into a single pipeline, giving cleaner, modular code without deeply nested loops or intermediate collections.
- **Rich transformation/aggregation support** — built-in collectors such as `groupingBy()`, `partitioningBy()`, and `reducing()` express common data-processing tasks without manual bookkeeping.

## 5. Common Pitfalls When Using Streams

- **Non-interference violations** — mutating the underlying collection while a stream processes it can disrupt traversal order or throw `ConcurrentModificationException`. Streams assume the source stays unchanged during pipeline execution.
- **Harder debugging** — fluent, often deeply nested chains of transformations make it harder to set breakpoints or inspect intermediate values compared to traditional loops.
- **Reusing a stream** — streams are single-use. Once a stream's operations have executed and produced a result, trying to reuse the same stream instance throws `IllegalStateException`. Create a new stream for each traversal.
- **Side effects in lambdas** — `map()`/`filter()` lambdas that modify external state risk subtle bugs, especially under parallel streams, and undermine predictability. Stream operations work best with pure functions.
- **Overuse** — for very small collections or simple, one-step tasks, a traditional loop can be more straightforward and efficient. Streams pay off when their abstraction genuinely improves clarity or simplifies complex transformations.

## 6. Path Forward

Understanding streams' mechanics matters because of **delayed (lazy) execution** — things don't necessarily run when they appear to in the code, which can be confusing without a solid grasp of when the actual work happens. Later lessons dig into these mechanics to use streams effectively and avoid unexpected behavior.
